# T-001 expectations, draft A (expect-A)

Task: Core module (events bus, service registry, IDs, feature flags, clock, save contract). IDs: D-003, D-004, F-009, F-043, M-008 (text as quoted in `tasks/T-001.md`).
Written before any implementation exists. Test names below are suggestions; the implementer may rename them if `EVIDENCE.md` maps each criterion to the real test name.
Style references: none apply (no visual output). The only "look" that matters is that a later agent can read `MODULE.md` and add a module in minutes.

## 1. Acceptance criteria

**Structure and independence (MODULARITY §1, §3)**
1. `Core.Contracts` and `Core` assemblies are engine-free (`noEngineReferences: true`) and reference nothing outside the .NET base library. Exactly one adapter assembly references `UnityEngine`. Artifact: asmdef files in the diff, plus `dotnet build` of `DotnetTests/` succeeding with no Unity DLLs on its reference path.
2. The same test source files run under both `dotnet test` and Unity EditMode, with the same test count and all passing in both. The dotnet project compiles Core with the language version and API surface Unity 6000.6 supports (no API that compiles under dotnet but fails in Unity). Artifact: TRX + EditMode XML with matching totals.
3. Unity compile log for the task branch shows 0 errors and no warnings coming from `Assets/Game/Core/`. Artifact: log excerpt.
4. **Extension proof:** a test-only "sample module" (in a test assembly, not in Core) defines its own event type, its own service contract + implementation, its own feature flag and its own save record type, and works end to end, with zero edits to Core sources. Test: `ExtensionProof_SampleModule_NoCoreChanges`. This is the main thing a later feature author needs from Core.
5. `Assets/Game/Core/MODULE.md` fills every field of the MODULARITY §6 template (purpose, breakdown IDs, contracts with versions, events consumed/emitted, config assets, flags, tests, owner role, known limits with `Q-` links), plus a short "how to use" example for each of the six services. Artifact: the file.
6. `.gitignore` exception is narrow: `DotnetTests/` project files are tracked; Unity-generated `*.csproj`/`*.sln` at the root stay ignored. Artifact: `git check-ignore -v` output for both. Every new asset/folder under `Assets/` has its `.meta`.

**Event bus (F-009, M-008)**
7. Same-step delivery: an event published at simulation step k reaches every subscriber before step k ends, never deferred to a later step, frame, `LateUpdate` or coroutine. Test: `Bus_DeliversWithinPublishingStep` asserts each handler observes the clock at tick k.
8. Deterministic order: dispatch order is defined and documented in `MODULE.md` (e.g. subscription order), independent of hash codes, GC or type-load order. Two runs of the same scripted scenario (several event types, ≥ 10 subscribers, subscribe/unsubscribe churn) produce byte-identical dispatch traces. Test: `Bus_DispatchOrder_IsDeterministic` with the trace hash recorded.
9. Re-entrancy has defined, tested semantics: (a) publishing from inside a handler delivers the nested event in the same step, in a documented order relative to the outer event; (b) unsubscribing a not-yet-called handler during dispatch means it is not called; (c) unsubscribing yourself during dispatch is safe; (d) subscribing during dispatch takes effect at a documented point (recommended: from the next publish). Tests: one per case, `Bus_Reentrant_*`.
10. A throwing handler does not stop the others; remaining handlers still run in order; the exception is surfaced (reported through a Core error sink that tests can assert on, and logged by the adapter), never silently swallowed. Test: `Bus_HandlerThrows_OthersStillRun_ErrorReported`.
11. Zero allocation (M-008, Core's part): after warm-up, 10,000 publishes of a struct event with 1, 8 and 64 subscribers allocate 0 bytes on the managed heap, in both the dotnet run and the Unity EditMode run (Mono). Events are not boxed. Reading a flag and reading the clock also allocate 0 bytes. Test: `Bus_Publish_ZeroAllocSteadyState` printing bytes per scenario.
12. Events are typed: subscribing to one event type never receives another; no string topics. Test: `Bus_TypedIsolation`.
13. Informational (cannot fail, no registered metric yet): ns per publish per subscriber on the dev Mac, recorded for later budgets. Proposed `M-NEW-a` below.

**Service registry**
14. Register/resolve by contract type. Resolving a missing contract and registering a duplicate both fail immediately with an error naming the contract type (no `null`, no silent overwrite). Tests: `Registry_MissingResolve_Throws`, `Registry_Duplicate_Throws`.
15. No hidden global state: two registries (and two buses) in one process are fully independent; the whole Core test suite passes in any order and repeated in one process. A scan of Core sources finds no mutable `static` fields. Artifact: test run with randomised order + grep output.
16. Unity lifecycle: entering Play Mode twice in one editor session with domain reload disabled starts with a fresh registry, bus and flag snapshot both times (nothing from the last session leaks). Test or scripted check: `Adapter_ReenterPlayMode_FreshState`.

**IDs (F-043, D-004, D-003)**
17. ID types are distinct value types: an entity ID cannot be passed where a building ID or player slot is expected (compile-time). Equality, hashing and ordering are value-based and allocation-free. Artifact: contracts in the diff; test `Ids_ValueSemantics`.
18. Stable and deterministic: the same source input always yields the same building ID across processes, machines and runs (no `Guid.NewGuid`, no `string.GetHashCode`, no allocation-order dependence). Every ID round-trips through its string form and the save format losslessly. Test: `Ids_RoundTrip_AndStableAcrossProcesses` (golden values checked into the test).
19. Building IDs have room for real map data: full 64-bit OSM-sized identifiers (values above 2^32 round-trip), and IDs from different sources (OSM way vs relation, hand-made landmarks F-041) cannot collide. Test: `BuildingId_LargeValues_NoCrossSourceCollision`.
20. Entity IDs are never confused after reuse: an ID released and reallocated never compares equal to the old one (permadeath D-020 means stale references must be detectable). Test: `EntityId_StaleAfterReuse`.
21. No hard-coded counts (D-004, D-003): the player-slot model and every Core collection work for N = 1, 2, 8 and 64 with no code change; Core contains no literal player, mech, kaiju or pilot count and no type that assumes one player maps to exactly one mech. Tests: parameterised `PlayerSlots_SupportN(1,2,8,64)`; grep artifact for literal `2` used as a count.

**Feature flags (Rule 5)**
22. Flags load from `Assets/Game/Config/FeatureFlags` via an engine-free model; the committed file lists every known flag set to **off**. Unknown flag name reads off. Missing or malformed file: every flag reads off and a clear error is reported; it never turns anything on. Tests: `Flags_UnknownIsOff`, `Flags_MissingFile_AllOff`, `Flags_Malformed_AllOffAndReported`.
23. A module adds its own flag without editing Core code (covered by criterion 4). Flag values are a snapshot fixed for a session (deterministic; host can later replicate one snapshot). Test: `Flags_SnapshotImmutableDuringSession`.

**Clock**
24. Fixed step in seconds comes from config, not a literal, and is the single source of truth for Unity's fixed step (adapter sets or verifies `Time.fixedDeltaTime`; a mismatch is reported). Engine-free code reads step length and an integer tick count. Simulated time after 10^6 steps equals tick x step with no accumulated float drift. Tests: `Clock_NoDriftOver1e6Steps`, `Adapter_FixedStepMatchesConfig`.

**Save contract (F-043)**
25. Versioned: every save file carries a schema version; loading a newer version fails explicitly; loading an older or unknown version never yields silently wrong data (either a registered migration runs or loading fails with a clear error). Tests: `Save_NewerVersion_Rejected`, `Save_UnknownVersion_NoSilentLoad`.
26. Round-trip: ID-keyed records written and read back are equal, record for record, including large IDs from criterion 19; output is deterministic (same data gives byte-identical file, stable ordering) so saves diff cleanly. Test: `Save_RoundTrip_Deterministic`.
27. Crash-safe: an interrupted write never destroys the previous good save (the world save holds persistent destruction, D-016; losing it is the worst outcome). Test: `Save_InterruptedWrite_PreviousSaveIntact`.
28. Modules own their own record sections; Core knows nothing about buildings. Informational: write+read time and file size for 100,000 small ID-keyed records, recorded for the later F-043 task.

## 2. What would disappoint the founders
- Over-engineering: a reflection/attribute auto-wiring DI container, async or threaded message queues, priorities, string topics, plugin loaders, generic "framework" layers nobody asked for. Core should be small and boring; if it reads like a framework, it is wrong.
- A bus that reorders, batches or delays events to a later frame (breaks F-009 footfall coupling), or whose order depends on dictionary hashing.
- Static singletons or service locators reachable from anywhere; state that survives between tests or Play Mode sessions.
- Flags that default on, a missing flag file that enables things, or a flag read that allocates.
- Any `UnityEngine` reference in Core or Contracts; tests that only run inside Unity; a second copy of tests for dotnet.
- Hidden `2`s: `Player1/Player2` fields, `players[2]`, max-player constants in code, one-pilot-per-mech assumptions.
- IDs from `GetHashCode`, `Guid.NewGuid`, `GetInstanceID` or spawn order; 32-bit building IDs that will overflow on OSM data.
- A save format with no version field, nondeterministic key order, or a write that can leave a half-written file.
- Exceptions swallowed in handlers; "zero-alloc" claimed without a measured number from both runtimes.
- A `MODULE.md` that is a stub, or an API a later agent cannot use without reading Core internals.
- Gameplay event types (FootContact etc.) defined in Core; world/building save content built early.

## 3. Evidence the implementer must produce (in `evidence/T-001/`)
- `EVIDENCE.md`: one table row per criterion above: criterion #, test name(s) or artifact path, the exact command, commit hash, result. Plus tool versions (dotnet SDK, Unity 6000.6.9f1, OS/machine).
- `dotnet test` TRX and console log; Unity EditMode results XML; both showing totals and the same test names.
- Allocation output: bytes per scenario (1/8/64 subscribers, flag read, clock read) for dotnet and Unity, plus the informational ns/publish figure.
- Determinism trace hashes from two separate process runs (criterion 8) and golden ID values (criterion 18) from two processes.
- Unity compile log excerpt (0 errors), and one sample save file produced by the round-trip test so the format and version field are visible.
- Grep outputs: mutable statics in Core, `UnityEngine` usage outside the adapter, literal counts; `git check-ignore -v` output.
- Every evidence item is reproducible by an evaluator with one command listed in `EVIDENCE.md`, without reading the implementer's notes.

## 4. Open points (proposed `Q-NEW-*`, each with recommended default, marked Assumed if unanswered)
- Q-NEW-a: Nested publish order: depth-first (nested event delivered immediately, inside the outer dispatch) or queued until the outer dispatch finishes, still within the same step? **Default: queued then drained before `Publish` returns (breadth-first)**: predictable order, no deep recursion, same-step guarantee kept.
- Q-NEW-b: Threading: may other threads publish? **Default: simulation thread only; publishing from another thread fails loudly in development builds.**
- Q-NEW-c: Flags at runtime: can a flag change mid-session (debug toggles)? **Default: no; snapshot at boot. A debug override file may change values at next boot only.**
- Q-NEW-d: JSON with only the .NET base library means a small hand-written serialiser; allow `Newtonsoft.Json` (Unity package + NuGet) inside Core implementation only? **Default: no dependency; a minimal serialiser for the save/flag formats, swappable behind the save contract (binary later if Bay-scale saves are slow).**
- Q-NEW-e: Building ID source for OSM buildings: OSM type + id, or our own stable IDs assigned at import? **Default: (source namespace, 64-bit source id), so re-imports of updated OSM data keep IDs; landmarks get their own namespace.**
- Q-NEW-f: One static composition root in the Unity adapter is probably needed for MonoBehaviours to reach the registry. **Default: allow exactly one, in the adapter only, reset on Play Mode entry (criterion 16), documented in `MODULE.md`.**
- Q-NEW-g: Size guideline. **Default: Core + Contracts (excluding tests) under about 1,500 lines; larger needs a reason in `MODULE.md`.**
