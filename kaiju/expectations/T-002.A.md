# T-002 expectations, draft A (expect-A): headless metric tools for M-001 to M-004

Status: draft, independent of draft B. Specs are binding as written (`M-001@v1`, `M-002@v1` in R-001 §9; `M-003@v1`, `M-004@v1` in R-002 §4-5). "Assumed" thresholds stay Assumed until founder calibration. Outcomes only; no implementation choices.

## 1. Acceptance criteria (each is gating unless marked)

**Coverage and fidelity**
1. Every sub-measure is implemented, reported by ID, with value, threshold, margin and pass/fail/N-A: M-001.1-.13; M-002.1-.5 (M-002.2 reported only, not gating); M-003 a (A_2 on `color_output` and on `color_internal`, plus A_3/A_5 informational), b (DIG gate; O and DIG<=0.5 advisory), c1, c2, d-i, d-ii, d-iii (advisory), d-iv, e (advisory: sky share, horizon, silhouette contrast), f; M-004 S0, S_px, C_px, F for each motion class (S0, Y1-Y2, T1-T2, T3). Test: `test_registry_covers_spec` compares the report's ID list to the spec IDs and fails on any extra or missing ID.
2. Verdict rules match the specs exactly: M-001 PASS only if all 13 pass; M-002 PASS only if .1 and .3-.5 pass; M-003 PASS only if a, b, c1, c2, d-i, d-ii, d-iv and f pass; M-004 PASS only if every required sequence passes every motion-class threshold. Test: for each gating ID, one fixture failing only that ID yields FAIL; one failing only an advisory ID still PASSes and shows the advisory warning.
3. Correctness on synthetic fixtures with known answers, generated by script from closed-form truth (not by calling the tool's own functions) and seeded: gait logs of known Fr, stride period, duty factor, CoM and yaw accelerations, start and stop times, slip per contact; images of known A_2, known DIG (Bayer, white noise, none), monotonic and non-monotonic depth banding, a `haze_cal` set, known posterisation, hue and grid integrity; frame sequences of known S_px, C_px, F under translation and yaw. Test names carry the sub-measure ID (`test_M001_4_*`, `test_M003_d4_*`). Measured values equal truth within a stated tolerance (<= 1% relative, or <= 0.005 absolute for shares).
4. Each sub-measure has a boundary pair (value at 98% and 102% of its threshold: pass, then fail) and at least one negative control that must fail. The R-002 controls are reproduced: unquantised render fails a (0.847), bilinear upscale fails a and d-iv, inverted and no-haze scenes fail c1 and c2, posterised-no-dither and continuous ramp fail b, screen-fixed dither under yaw and temporal-noise static fail M-004.
5. CIEDE2000 matches the published Sharma 34-pair reference table (<= 1e-4), and sRGB-to-Lab matches known D65 values. Test `test_ciede2000_sharma`.
6. Worst case is never averaged away. M-001 and M-002 report per capture and per contact; the verdict uses the worst capture. M-002.1 is the maximum over all contacts of all captures and names the worst 5 (capture, foot, contact id, time). One 0.12 m slip among 200 good contacts must FAIL. A single-step acceleration spike is reported as an unsmoothed peak next to the smoothed one (informational) so smoothing cannot hide it silently.
7. **No pass on missing or malformed input.** Verdicts are PASS, FAIL, INVALID_INPUT (contract violation) or INCOMPLETE (valid but required evidence absent). Only PASS exits 0. Vacuous cases are INCOMPLETE, never PASS: zero contacts, fewer than 3 steady strides, zero strides, no evaluated dither frames (all < 5% gradient), fewer than 3 depth bands for c1, sequence or capture missing from the required set, fewer than 12 frames per profile, sidecar missing, panel scores absent (M-001.13, M-003 f), valid-pixel fraction below the registry minimum. Tests cover each case, plus truncated JSONL, NaN or inf, wrong schema string, wrong units, bad PNG bit depth, mismatched file hashes, sidecar and image disagreement.
8. Panel items (M-001.13, M-003 f) are ingested from a documented, validated ratings file (rater id, blind flag, anchor scores, capture, score). The tool applies the specs' rules (n >= 3 or >= 8 raters, anchors, rater exclusion, medians or means, per-scenario and per-profile floors). Without that file the metric is INCOMPLETE with the headless sub-measures still reported. The tool never fabricates or defaults a score.
9. **Thresholds only in a versioned registry** under `Tools/Metrics/registry/`. Each entry has sub-measure ID, value, unit, status (`derived` or `assumed_pending_calibration`) and source reference. Test: for every threshold key a temp registry with the value moved across the boundary flips the verdict with no code change; a source scan finds no spec threshold literals outside the registry and tests. The report prints registry version and hash, and lists every Assumed threshold that was decisive (PASS reads "PASS (provisional: n assumed)").
10. **Reports are complete and reproducible:** JSON with metric ID and version (`M-00x@v1`), registry version and hash, tool version and git commit, each input file path and SHA-256, header-derived normalisers (l, L_f, m, g, F_on, F_off), every sub-measure as above, verdict, exit code, and the coverage list (required vs provided vs missing, optional items such as the non-flat-terrain walk marked "not provided"). A short human summary (<= 40 lines) lists failing IDs first. Optional diagnostics (dE heat map, slip plot, shimmer map) are written headless, with a deterministic name.
11. **Determinism:** two runs on the same inputs give byte-identical reports once the declared `run` block (time, host) is stripped; fixed seeds; independent of thread count and of the machine's locale and GPU.
12. **Speed, headless:** no display needed (`DISPLAY` unset passes). Each metric finishes in < 60 s on its typical input (default reading in section 4), with the timing recorded in the evidence.
13. **Validators** for `gait_log@v1`, `style_capture@v1` and `palette_set@v1` run standalone (`validate` command, exit 0 or 2, machine-readable list of all errors, not only the first, each with file, line or key path, expected vs found). They enforce at least: R-001 §8's five checks (header complete, `n` contiguous, t = n*dt within 1e-9 s, feet length equals foot_ids, `source_n` references a real `contact_begin`), `event` follows its `step`, finite numbers, unit quaternions and unit `cn`, positive mass and dt, header thresholds present; for captures: required files per frame, bit depths, resolutions equal sidecar, depth decode within near/far, `palette_index` values within profile size or 255, the same frame index across all files, `palette_sha256` equals the declared profile's hash, no TAA or blur flags in `build.feature_flags` contradicting rule 2; for palettes: hex format, Lab consistent with hex (tolerance stated), `ramp_*` order complete, profile colour counts. Each rule has a good and a bad fixture.
14. **Gaming guards:** header normalisers (`leg_length_m`, `mass_kg`, `length_m`, `thresholds`) that differ from the reference-mech registry entry are printed as `NON_REFERENCE_NORMALISERS` in the summary; header F_on/F_off differing from 0.03 m g / 0.01 m g is reported with the contact-count effect (M-002.4 uses the spec values, not the implementation's). M-004 checks that camera motion measured from the sidecar poses matches the declared `motion` speed (stated tolerance) and that frames are not degenerate (blank, frozen, or fully masked), else INVALID_INPUT. A black or frozen sequence must not pass.
15. **Usability by other agents:** one obvious documented command per metric plus `validate` and `list-metrics`; `--help` shows inputs and exit codes; errors say what, where and how to fix (no stack traces for bad input); exit codes 0 PASS, 1 FAIL, 2 INVALID_INPUT, 3 INCOMPLETE, documented and tested; kaiju env only, any new dependency added to `environment.yml`; README (per-metric run, inputs, outputs, how to add a metric version or a registry revision) and MODULE.md exist and every command in them is exercised by a test.
16. **Reference-panel baseline** stored under `evidence/T-002/baseline/`: the still-applicable measures (a, b, d-i, d-ii, d-iii, e-contrast) on the 11 reference panels using the R-002 caption/logo masks and per-panel profile. Values reproduce R-002 (raw A_2 0.63-0.85, ref_06A 0.16; the DIG table within +-0.02; hue and level counts equal). The baseline is honest: references that fail A_2 or d-iv stay failing, thresholds are not touched, and the verdict for stills is "N/A: not a capture set" rather than PASS. Per-panel JSON, one summary table, and the commit hash of the registry used.

## 2. What would make a tool worthless or misleading
- A PASS built on nothing: zero contacts, one stride, all dither frames skipped, a single depth band, an all-sky depth map, or an animated mask covering the frame.
- Means or p95 hiding the one bad foot-plant, the one worst yaw spike, or the worst of 36 sequences.
- A black, blurred or frozen capture scoring perfect M-004; a white-noise or temporal-noise render passing DIG (it scores 0.58 per R-002) with no warning on O.
- Thresholds edited, loosened or Assumed values silently treated as final to make an early build pass; a decisive Assumed threshold not shown in the report.
- Trusting the implementer's header: shrunken `mass_kg` or inflated `leg_length_m` loosening limits, a self-reported `contact` flag replacing the force hysteresis, float32 positions called float64.
- Numbers that change between runs, or tests that compute expected values with the same code they test (circular proof).
- Output that omits input hashes or versions, so a past verdict cannot be re-checked.
- Reports that read as one number without margin: nobody can tell 0.099 m from 0.01 m against 0.098 m.
- Silent unit or axis slips (left-handed Unity frame, yaw sign, degrees vs radians) that pass synthetic data generated with the same mistake: fixtures must include a hand-computed non-axis-aligned case.

## 3. Evidence the implementer must produce (`evidence/T-002/`)
- `pytest` output (full, with test IDs per sub-measure and a coverage matrix: sub-measure ID to test names to fixture ids), command and commit.
- JSON reports and summaries for every fixture, positive and negative, per metric, including boundary pairs.
- Validator runs: good and bad fixtures for the three contracts with their error output.
- Registry files, registry-flip test output, and the source scan result for threshold literals.
- Determinism proof (two runs, diff of stripped reports), timing table per metric on the typical input, headless run log.
- Reference-panel baseline reports and table (criterion 16), plus fixture generator scripts and seeds.
- Exit-code table run live for each metric (0, 1, 2, 3 each shown).
- `EVIDENCE.md` mapping each criterion above to its artifact path, and the list of spec defects found (section 4) with proposed `Q-###`.

## 4. Spec ambiguities and recommended readings (report as defects against the spec; do not silently change)
1. M-001.13 and M-003 f need human scores but define no file format: define the ratings file in the README; headless sub-measures run without it and the verdict is INCOMPLETE (exit 3).
2. M-001.6 "(P - c m g v)/(m v)": `c` is undefined. Recommend: read `c` and P from the registry and header (P = `reactor_power_W`); mark the power-limit half Assumed until R-001 defines `c`, report it separately from the 0.14 g half.
3. M-001.12 "m v / F_brake,max": F_brake,max undefined, and "check across >= 2 mass variants" cannot be done with one log. Recommend: gate only the 3.1 s floor now; report the mass-scaled term as N/A until a variant log exists.
4. M-001.10/.11 "steps" and "t*" undefined. Recommend: steps = stride time / 2 (one step per foot contact_begin) and t* = time-to-stop in units of T_nom/2. Test both on a fixture whose answer differs by 2x so a wrong reading shows.
5. M-001.4/.5 axes: "fore-aft" and "lateral" are relative to heading. Recommend: project horizontal CoM acceleration on root yaw; peak over all samples after smoothing; applies to every capture including estop.
6. M-001.3 and .2: double support and stride period definitions are implicit. Recommend: T_meas = same-foot contact_begin to contact_begin, median over steady strides; duty factor from the hysteresis contact intervals.
7. M-002 contact edge cases: contacts truncated by log start or end, and zero-length. Recommend: include them in max slip, tag `truncated`, never drop. The 20-stride non-flat walk is optional; report "not provided". Stomp: M-002.5 requires 0 excluded, so a stomp with `ext_f` > 0.05 m g makes M-002.5 FAIL (as written).
8. M-003 b: window stride, and how a pixel is counted when several windows overlap, are unspecified. Recommend: sliding 4x4 windows, stride 1, a pixel is interleaved if any covering window qualifies; tool reproduces the R-002 validation values on the shared controls (Bayer 0.70, white noise 0.58, none 0.00, ramp 0.01, each +-0.03).
9. M-003 verdict text lists d-i to d-iv as gating but d-iii is "Advisory". Recommend d-iii advisory; c2 gates through the `haze_cal` set, so a capture set without `haze_cal` is INCOMPLETE.
10. M-003 c2: ΔL* is signed in the validation table (4.3 to -1.3, "non-increasing"). Recommend signed light minus dark, noting ramp noise produces small negatives; the 8 km <= 50% of 200 m rule stands.
11. M-003 a: "255 count must equal the internal-capture failures" is ambiguous. Recommend: compare the 255 count with the count of `color_internal` pixels beyond T and report any mismatch as INVALID_INPUT (inconsistent capture).
12. `palette_sha256`: canonical form not defined. Recommend SHA-256 of the UTF-8 profile `colours` list serialised as compact JSON with keys sorted; document it and validate against it.
13. M-004 sequence classes: mapping from `motion.type` + speed to S0/T1/T2/T3/Y1/Y2 is by nominal speed only; `pitch` and `dolly` have no thresholds. Recommend nearest-nominal match within +-10%, otherwise INVALID_INPUT; pitch and dolly sequences are validated and reported without a verdict (never counted as pass).
14. M-004 F: "A to B to A" is stated on indices; recommend it is measured after reprojection (identical to plain difference when static). Minimum valid-pixel share (occlusion test, bounds) is unspecified: registry default 0.5, Assumed.
15. The reprojection needs rendered-pose precision: floating-origin local plus `origin_offset_m` must be recombined in float64; test with an origin offset of 50 km.
16. M-001 smoothing at 0.05 T_nom can attenuate a one-step shove; kept as written, hence the unsmoothed peak in criterion 6.
17. Speed: 60 s for "a typical input" is unattainable for the full M-004 set (36 sequences x 180 frames in Python). Recommend: typical = one profile-viewpoint set (6 sequences) < 60 s; the full set < 10 min with deterministic parallelism; M-001/M-002 full eight captures < 60 s; M-003 one capture set of >= 12 frames per profile < 60 s.

## 5. Open points for the founders (defaults assumed; none blocks work)
- Q-a: Should a PASS that rests on Assumed thresholds count as a gate pass before calibration? Default: exit 0 with the "provisional" label; evaluators treat it as provisional until the first calibration checkpoint.
- Q-b: Version bump on calibration. Default: spec stays `@v1`; any registry change creates registry revision rN and metric `@v1.N`, so past verdicts name the thresholds they used.
- Q-c: Which dither type is "right" (R-002 Q-NEW-a)? Default: DIG gates, O advisory; this task does not decide.
- Q-d: Who produces panel ratings and in what format? Default: founders plus blind agent raters per R-002 f, via the ratings file; metrics stay INCOMPLETE until supplied.
- Q-e: Warn or block on `NON_REFERENCE_NORMALISERS` (kaiju and variant mechs are legitimate)? Default: warn loudly in report and summary; no block.
- Q-f: Exit code 3 for INCOMPLETE: acceptable for CI use, or should it alias 1? Default: keep 3, documented.
