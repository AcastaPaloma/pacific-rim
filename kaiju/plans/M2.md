## Track 1 · Full 1:1 Bay geo bake (P3, P4)

- **Goal.** Every BayTM@v1 L0 tile that intersects the Bay world box and holds land or water bakes through the existing
  `geo_tile@v1` pipeline with no code fork (`bake_tile.py` is already tile-id-parameterised over the 68 × 68 grid).
  Includes: building heights outside San Francisco (no DataSF there: lidar DSM fill as in T-020b, county sources where
  licensed), all Bay landmarks of F-041 (Bay Bridge both spans, San Mateo, Richmond–San Rafael, Dumbarton, Port of
  Oakland cranes, Alcatraz, SFO/OAK runways), and the infrastructure layer of F-044.
- **Modules and contracts.** `Pipelines/geo` (`geo_tile@v1`, unchanged; new `bay_manifest@v1` listing tiles, their
  coverage class, source fingerprints and bake status). Landmarks extend `config/landmarks.json` (sourced only). New
  `infrastructure` layer slots after `landmarks` (LayerApi 1, `IGeoLayer`): `infra@v1` records keyed by Core IDs
  (`InfraId`: bridge, power substation/line, port crane, airport runway/terminal), from OSM `power=*`, `man_made=crane`,
  `aeroway=*`, bridges from `bridge=yes` + landmarks.
- **Storage (decided, Q-200).** The 15 district tiles stay committed (LFS). Bay tiles are **baked into the git-ignored
  cache** (`Pipelines/geo/cache/bake/tiles/v1/`), reproducible from the fingerprinted manifest, and copied into
  `StreamingAssets` only by the player build step (M3 Track 1). Reason: ~1–3 k tiles × 5–15 MB would put tens of GB in
  LFS on every clone; determinism already makes the cache authoritative. Alternative (commit everything to LFS) rejected
  for clone cost, not fidelity.
- **Depends on.** Nothing in M1. Free disk 448 GB (2026-11-15); expected raw download ≈ 40 GB (R-004: CUDEM 5.0 GB,
  3DEP 33.8 GB, OSM NorCal 0.66 GB, water 0.9 GB) plus lidar EPT windows for height fill.
- **Research.** R-100: Bay tile coverage set and classes (urban / rural / water-only / outside); data volume and fetch
  time per source; building-height sources outside SF (lidar DSM fill per county, Alameda/San Mateo/Santa Clara/Marin/
  Contra Costa open footprint datasets and their licences); landmark sources for every F-041 item; infrastructure
  sources for F-044; M-005@v2 Bay-scale sampling plan (which landmarks, NGS benchmarks, bathymetry spots, viewpoints).
- **Gated on.** **M-005@v2** (Bay scale: M-005@v1.2 sub-measures over every baked tile, landmark rows for every F-041 item,
  default-height share ≤ 2 % by area Bay-wide and per county, bathymetry spot checks Bay-wide), M-100 (bake
  reproducibility: two runs byte-identical per manifest fingerprint), M-008 (bake is offline; runtime cost is Track 2's).
- **Tasks.** T-100 coverage manifest + `bay_manifest@v1` (Python, 2 steps). T-101 bulk fetch driver, resumable and
  backgrounded, one source per run (Python, 3 steps, long jobs write status files). T-102 Bay bake driver (parallel,
  resumable, per-tile status; 2 steps + background run). T-103 height fill outside SF (lidar DSM fill generalised + county
  footprints, 3). T-104 F-041 landmarks Bay-wide (sourced; bridges measured from lidar like T-023; 4). T-105 F-044
  `infrastructure` layer bake + `World.Infrastructure` engine-free registry (`IInfrastructureRegistry`, InfraId, damage
  hookup through `IDamageModel`) (4). T-106 M-005@v2 tool + Bay run (`m005_check.py bay`) (3).
  Evaluators (one combined, §13): eval-bay + eval-arch. **≈ 21 steps + 1 research.**

## Track 2 · Bay streaming, LOD, floating origin at Bay scale (P3, P4, P1)

- **Goal.** A player can traverse the whole Bay (Golden Gate → San Jose ≈ 75 km, Richmond → Dumbarton) with tiles
  loading ahead of the camera and kaiju, no hitch above budget, the pixel look unchanged at every LOD, and simulated
  bodies kept within the float32 bound. Destruction state persists for tiles that unload (F-043).
- **Modules and contracts.** New `World.Streaming` (L2; Core + `World.Geo.Contracts`): engine-free scheduler
  (`IStreamingFocus` set: every camera, mech and kaiju; residency rings per LOD; priority by distance, velocity and
  screen-space error; memory budget; load/unload events `TileResident`, `TileEvicted` on the Core bus, unmanaged, IDs
  only). LOD contract `geo_lod@v1`: L0 native, L1–L4 terrain pyramids (2×, 4×, 8×, 16×) and building impostors /
  merged blocks, baked offline in `Pipelines/geo` (`bake_lod.py`). Unity side `World.Streaming.Unity`: async IO, mesh
  build off the main thread, collider only within the physics ring, floating-origin rebase via existing World.Geo
  origin service. Flag `world.streaming` (default off).
- **Depends on.** T-021 multi-tile load and floating origin (merged). Track 1 for the full tile set (works on the 15
  district tiles first, then on the cache bake as it lands).
- **Research.** R-101: streaming budgets at 1:1 (IO MB/s, CPU ms per tile build, GPU memory per LOD), LOD selection for a
  pixel-art renderer (screen-space error in **output pixels**, not internal), how far a 300 m skyline must stay visible
  (haze-limited draw distance from R-002/R-003 depth bands), physics ring radius vs fastest body (thruster lunge, kaiju
  charge), destruction persistence for unloaded tiles, prior art (Unity terrain streaming, flight-sim tiling).
- **Gated on.** **M-015@v2** (Bay traversal ≥ 75 km with mechs and kaiju simulated, every body ≤ 4096 m, round-trip
  ≤ 1 mm), M-101 (streaming hitch: no frame > 33.3 ms from streaming on a scripted 75 km flythrough, p99 frame within
  M-013), M-102 (LOD pixel error: at each LOD switch distance the output-pixel difference vs L0 ≤ 1 px RMS silhouette
  and ΔE ≤ 2.0 on ≥ 99 % of pixels; no popping across switch frames per M-004), M-005@v2 skyline rows from Bay
  viewpoints, M-008 at Bay scale.
- **Tasks.** T-107 `World.Streaming` contracts + engine-free scheduler + dotnet tests (4). T-108 `bake_lod.py`
  terrain pyramids + building impostors (Python, 4). T-109 Unity loader: async IO, mesh/collider rings, rebase (4,
  Unity). T-110 destruction persistence across evict/reload (save section `streaming@v1` or reuse `destruction@v1`;
  2). T-111 flythrough harness + M-015@v2/M-101/M-102 tools (3, Unity + Python).
  Evaluators: eval-perf + eval-arch, eval-style on LOD captures. **≈ 17 steps + 1 research.**

## Track 3 · Three kaiju species and pack behaviour at Bay scale (P5, P2, P1)

- **Goal.** Three original species across D-026's mass categories, each with a sourced biomechanical spec (mass from
  structure as §4, graviportal gait timing F-023, limb and contact geometry, attacks with impulse budgets), one shared
  observation/action architecture and one policy per species (F-025), and pack behaviour that M-007 measures at Bay
  scale: emergence on real faults across the Bay (F-020), roaming to F-044 infrastructure targets, pack formation
  across species (light baits/flanks, heavy anchors), and focus fire.
- **Modules and contracts.** `Units.Kaiju` (L2): `KaijuSpeciesSpec@v1` data (engine-free, derived numbers with sources),
  `species/*.json`. `AI` gains a pack layer in a **new** assembly `Game.AI.Pack` (consumes `Game.AI.Contracts` only;
  does not edit M1's `Game.AI.Scripted`, `Harness` or T-041's `Policy`): pack roles, shared target board, infrastructure
  goal selection over `IInfrastructureRegistry`. `World.Emergence` (L2): Bay-wide emergence site selection from
  `World.Seismic` ruptures. Harness scenario `m007_bay` (N species, Bay-scale map with infrastructure).
- **Depends on.** M1 T-033b scenario format (merged), T-041 policy architecture (running under M1; Track 3 consumes its
  contract, never edits it), Track 1 T-105 for real infrastructure (synthetic targets first). **Kaiju locomotion and
  physics bodies** wait on T-005's gait approach (staged, tracked: "M2-kaiju-body" row, owner Track 3).
- **Research.** R-102: three species biomechanics (scaling from elephants/sauropods, bone/muscle stress limits at 60,
  100, 160 m; mass from structure; Froude-band gait; attack types with impulse/energy; wading depth and buoyancy;
  silhouettes readable at 1–3 px per metre in the pixel style; **original designs only**, D-009). R-103: pack behaviour
  at Bay scale (heterogeneous packs, role allocation, infrastructure-raid vs hunt trade-off, M-007@v2: per-species and
  pack measures, mixed-species scenarios, infrastructure clauses, null and ablation controls per the R-024 rev 3
  addendum), plus the M-008 Bay scenario (2+ mechs, 3+ kaiju of mixed species, destruction, streaming).
- **Gated on.** **M-007@v2** (pack measures at Bay scale with species mix; win-rate clause against the scripted baseline
  once T-041 trains), M-103 (species physical consistency: mass/stress/gait per spec within sourced bounds), M-058
  (brain tick) extended to the pack layer, M-008 Bay scenario.
- **Tasks.** T-112 species specs + `Units.Kaiju` contracts + tests (3). T-113 `Game.AI.Pack` roles + target board +
  infra goals, pure C#, harness scenarios (5). T-114 `World.Emergence` Bay-wide site selection + emergence sequence
  events (3). T-115 M-007@v2 tool + `m007_bay` runs (3, Python). T-116 per-species policy training configs once T-041's
  architecture merges (staged; 3). T-117 kaiju physics bodies per species (staged on T-005; 6).
  Evaluators: eval-ai + eval-physics + eval-arch. **≈ 23 steps + 2 research.**

## Track 4 · Economy, salvage, permadeath, refit (P5, P2)

- **Goal.** The loop between fights: city defence contracts pay for builds and repair (D-024), salvage recovered from kaiju
  and wrecks by physical mass and material (D-024, F-010), a roster where a destroyed mech is gone for good with its
  salvage recoverable (D-020, F-010), and refit on one modular frame with two chassis classes (D-025, F-062) whose limits
  come from physics (mass, CoM, reactor power, heat, actuator torque). Hangar integration (F-060) through T-034's
  contracts.
- **Modules and contracts.** All engine-free, deterministic, save sections in the Core envelope:
  `Meta.Economy` (`economy@v1`: ledger of funds, contracts, transactions; prices derived from part mass × material cost
  index with sources). `Meta.Salvage` (`salvage@v1`: yield from destroyed parts/limbs and building debris mass,
  recovery fraction by damage state, rare-part rules). `Meta.Roster` (`roster@v1`: mech instances, permadeath on
  destruction event, wreck → salvage handoff, pilot record). `Meta.Refit` (`refit@v1`: modular frame slots, part
  catalogue `parts@v1`, validation of mass/CoM/power/heat/torque budgets, output `MechBuildSpec@v1` that Physics.Body
  will read once T-005 lands). Events on the Core bus: `ContractCompleted`, `MechLost`, `SalvageRecovered`,
  `RefitApplied`. Flags `meta.economy`, `meta.salvage`, `meta.permadeath`, `meta.refit` (default off).
- **Depends on.** T-025 save system and T-034 hangar (merged). Destruction `BuildingDamaged` and the placeholder damage
  record (merged) as salvage inputs. Mech part masses: the reference body data in T-005 (read-only; until it merges, the
  derived §4 numbers with a tracked "pending T-005 body" flag).
- **Research.** R-104: design spec. Contract payout model tied to protected value (infrastructure replacement cost,
  sourced), mech build cost by mass and materials (steel, titanium, composites: sourced cost indices), repair cost per
  damage state, salvage physics (recoverable mass by fragmentation; kaiju tissue as a material class for rare parts),
  permadeath rules and the anti-frustration floor (always enough funds for a basic Balanced chassis, D-020 without a dead
  end), refit constraints from physics, pacing targets. Sources for every number.
- **Gated on.** M-104 (economy pacing: in a seeded 30-campaign simulation, median sorties to replace a lost mech within
  the R-104 band, no unrecoverable state, no exploitable loop), M-105 (refit physical consistency: total mass, CoM,
  power and heat budgets of every valid build within the sourced limits; invalid builds rejected), M-106 (save round
  trips exact for all four sections over 3 cycles, as M-059), M-008 (negligible; checked).
- **Tasks.** T-118 `Meta.Economy` (4). T-119 `Meta.Salvage` (3). T-120 `Meta.Roster` permadeath (3). T-121
  `Meta.Refit` + `parts@v1` catalogue (5). T-122 composition installers + hangar adapter (2). T-123 campaign simulator
  + M-104/M-105 tools (3, Python). Evaluators: eval-arch + eval-physics (refit). **≈ 20 steps + 1 research.**
