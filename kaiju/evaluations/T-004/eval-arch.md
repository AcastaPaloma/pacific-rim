## Item 5: sub-pixel compensation and the validator
Cause: R-002 §6 puts `resolution.output_block_offset_px` and `subpixel_offset_internal_px` in every frame sidecar (per frame by nature, they follow the snap remainder), and `m003.py:125` reads them per frame. T-002's `style_capture.py:412-414` then requires the whole `resolution` block to be identical across a sequence. Verified on `cut_check/moving_then_cut`: 12 frames, 12 different offsets, internal/output/scale constant.
Decision: a **validator problem** (over-strict rule in T-002), with a **contract wording gap** in R-002 §6 (it never says which `resolution` fields are per-frame). `style_capture@v1` can express compensated output; it is not a pipeline problem (the pipeline writes exactly what the contract lists). Change: in `Tools/Metrics/kaiju_metrics/contracts/style_capture.py` compare only `internal_wh`, `output_wh`, `integer_scale` across a sequence and keep the existing per-frame range check at lines 174-177; add a fixture with varying offsets; add one sentence to R-002 §6 and `SPEC_READINGS.md`. No schema version bump needed (the schema text already allows it).
Effect on T-004: M-004 reads `color_internal` / `palette_index` (`m004.py:85,250`), which do not depend on the present shift, so C8-C10 values stand. But the M-004 sets were captured with `rendering.pixel.subPixelPresent` off while `M0StyleFrame.json` switches it on, so the stored `color_output` of those sets is not the shipped configuration. After the validator fix, re-capture one M-004 profile with the M0 flags unchanged and run `validate` plus the C11 check on it.
