## 1. Method
Render + one-pixel readback wall time, configs interleaved per frame, stage cost = paired difference, 300 frames, 40 warm-up. Sound as a *relative regression* tool on one machine, not as a GPU measurement:
- Wall time with readback is CPU submission + GPU + readback stall. Per-pass differences are dominated by per-pass overhead (encoder creation, render-graph setup, material block upload), not shading. Metal TBDR also folds adjacent passes and defers work, so removing a pass does not remove its tile cost.
- Noise is the same size as the signal: per-pass stdev ~0.13 ms vs means 0.07-0.14 ms. The chain is cheaper at 1440p (0.20) than at 1080p (0.25) although 1440p has more internal texels (512x288 vs 480x270): ordering evidence of noise or overhead dominance, not of pixel cost. Present max 6.0 ms in one 1080p frame (first frames: 1.7 ms vs 0.8 ms steady) shows warm-up/pacing spikes remain in p95-adjacent data.
- Vsync/pacing: frames are driven by a loop with explicit render calls, so vsync is likely off, but the artifacts do not say; frame pacing is not logged. 300 samples gives p95 from 15 samples: coarse.
- "Present" is the entire second camera (culling, graph, target clear, plus the capture render-request copy per `EVIDENCE.md`), not the one point-sampled pass the 0.5 ms budget in R-003 §9 means. The number cannot be compared to the budget.
- A proper measurement: GPU timestamps per named pass. In a player build: `FrameTimingManager` GPU time with `Pixel.*` `ProfilingSampler` markers (every pass here already has one: `Pixel.<Stage>`, `Pixel.Present`) read via ProfilerRecorder GPU recorders / Unity Profiler capture, or Xcode Metal GPU capture counters on the Mac; on Windows PIX / RenderDoc / Nsight. R-003 §9 says "measured with GPU markers per pass name `Pixel.*`". The implementer reports the GPU recorder needs a player loop in batch mode and did not build one. Missing per-pass GPU timing is a defect against C20 ("GPU p95 ... with per-pass breakdown"), see DEF-1.

## 2. Plausibility from code
Passes (all one DrawProcedural triangle, point filtered): downsample, haze, dither, quantise, store at internal 480x270 + guard (~0.13-0.15 MP, RGBA8; depth R32F; supersample camera target 2x, RGBA8 sRGB, so the downsample reads ~0.6 MP), LUT/palette lookups per pixel; present reads the internal texture and writes 1920x1080 (2.07 MP) or 2560x1440 (3.69 MP), 16-28x more written pixels than any stage. Bandwidth per stage is ~1-2 MB: R-003 §9 estimates 0.02-0.05 ms per pass on a discrete GPU; on an M-series part the true GPU shading time is likely well under 0.1 ms per stage. The reported ~0.1 ms per stage mean is therefore plausible as overhead-dominated wall time, and the 0.52 ms chain p95 is mostly noise and encoder cost. Present is the most expensive item because it is the only pass that shades at output resolution, and (as measured) it includes a second camera's whole setup and the capture copy. Pixels do not explain 0.44 ms alone; the camera overhead does. R-003 §9 budgets present at ~0.05 ms GPU, 0.3 ms CPU: the measured 0.74 ms is wall (CPU+GPU), so it is not necessarily a miss of the GPU line, but cannot be shown to pass either.

## 3. GC
Read `PixelStageFeature.cs`, `PixelPresentFeature.cs`, `PixelCameraBinder.cs`. Render functions are `static` lambdas over a pooled data class; one `MaterialPropertyBlock` per pass created once and `Clear()`ed; property ids cached; no `new` of reference types, LINQ or list growth in record/execute paths; `Vector4`/`Vector2Int` are structs; `PixelLog.WarnOnce` concatenates strings only on a stage-order violation. `AddRenderPasses` does a dictionary lookup, no allocation; materials created once. `PrepareFrame` (LateUpdate) not shown to allocate in lines read. Method gap: recorder is `CollectOnlyOnCurrentThread`, run in the Editor batch loop around render calls only, so render-thread/Metal-side native allocations and the capture path are not covered, and Editor `Camera.Render` is not a player loop. A 100-frame zero is consistent with my code read. No defect.
