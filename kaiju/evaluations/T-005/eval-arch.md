## Tests read critically (14 read; none is vacuous)
Good: `ArbiterSwap` (above); `IntentLimiterTests.InstantReversal`, `OverCommandedSpeed` (assert rates against limits and that the cause is reported); `NMechs_MechAIsUnchanged...` (real tolerance); `FootContact_IsPublishedOncePerContact_InTheContactStep` (counts events against flag edges, but the flag and the event come from the same state, so it is partly self-referential); `SingleJoint_DriveUnitsAndSign` (measures engine units); `MassUnit_...` (asserts both the sinking and the resting case); `Contract_HasExactlyTheModularity41Types`; `SinglePilotArbiter_IsTheOnlyShippedArbiter`; `LargeShove_EndsInAPhysicalFall`; `LegIk.Solve_*`.
Weak: `Contract_HasExactlyTheModularity41Types` checks field types of the listed types but not that no other public type exists, so "exactly" is not enforced (DEF-6). `DevicePilot_WithTheRealInputSystemDevices_ReadsWithoutADevicePresent` (ControlPlayTests.cs) only asserts `valid == true`, which the mapping always returns, and never injects device state (MODULE.md admits it). `FeatureFlags_OfTheseModules_ShipSwitchedOff` greps the JSON text for "true"; it proves nothing about behaviour (DEF-3). `Walk_ComesFromIntentOnly...` passes at Froude 0.02 (it asserts only Z > 60 m in 40 s), so it cannot guard the M0 walk target.

## Defects
**DEF-T005-arch-1 (major, C12): tuning numbers hard-coded in behaviour code.** `walk_tuning.json` carries 60+ values, but dozens of gains, thresholds and timings remain literals. Worst: `LocomotionController.cs:122` and `:390` (`Math.Sqrt(_l / 42.0)`: the reference leg length baked into every attitude, yaw and height gain, so the controller is tuned to one frame); `:163` (0.3 load filter); `:195` (1.0 s rest time before `Fallen`); `:220` (0.07 / 0.025 rad heading thresholds); `:261` (2.5 x shift time), `:260` (0.025 l DCM tolerance); `:272`, `:287` (0.12 step-time fractions); `:296-300` (0.9/0.1 transfer blend, 0.95, 1.6 x tds); `:330` (0.64 reach floor); `:335` (0.02 height rate); `:363` (0.06 l); `:399`, `:429` (friction / 1.5); `:473` (0.5, 3 clamp). `IntentLimiter.cs:76` (0.5, 2.4), `:88` (0.05), `:90` (0.8 yaw-accel fraction). `MechUnit.cs:95` (camera-impulse amplitude 0.05 and exponent 0.75). PASS: each of these is a named field in `walk_tuning.json` or `body_tuning.json`, or a documented mathematical constant.

**DEF-T005-arch-2 (major, C20): mech A is not independent of other mechs.** Stored `tests/unity_playmode.xml`: two PlayMode tests fail the 1 cm clause (2.0 cm with 2 mechs, 3.8 cm with 4, per EVIDENCE; the test's own doc comment still says 2.3 / 4.6 cm, so the comments disagree). MODULE.md "Known limits" says the same step count is "not bit-identical when other articulations share the scene". The cause is unresolved, and the 4-mech case is the D-004 use. PASS: the two tests green (a documented, tested cause, for example per-unit physics scenes or a fixed solver order, with mech A's CoM within 1 cm), or the clause re-negotiated in the spec by the orchestrator; and `KnownFailing` removed from the gate or excluded by a filter so the suite is not red by design.

**DEF-T005-arch-3 (minor, MODULARITY §1.5): feature flags are inert.** `physics.body.enabled`, `physics.body.physicsLog`, `units.mech.enabled`, `units.mech.gaitLog`, `control.devicePilot` are declared in JSON and as constants (MechUnit.cs:17) but no code calls `IsEnabled` (grep over the three modules: 0 hits). `MechSimulation.cs:28` builds its own snapshot with all four true, ignoring the shipped files. The module cannot be switched off, and the ship-off test only greps text. PASS: `MechUnit` / `DevicePilotSource` construction reads the flag from `IFeatureFlags` and refuses or no-ops when off, and a test flips it.
