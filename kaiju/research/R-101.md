# R-101: Bay-scale streaming, LOD, floating origin and destruction persistence (Track 2)

- **Agent:** M2 research worker · **Date:** 2026-11-15 · **IDs served:** T-107..T-111, M-015@v2, M-101, M-102, F-042, F-043, P3/P4/P1. New proposals: M-101, M-102 (drafts below), `geo_lod@v1`, `World.Streaming` contract.
- **Question.** What must a 1:1 Bay streamer do so that a player can cross ~75 km (Golden Gate to San Jose) with mechs and kaiju simulated, no streaming hitch, no visible LOD pop under the pixel pipeline, bodies inside the float32 bound, and destruction that survives eviction?
- **Confidence legend.** **H** read in a source; **M** derivation from cited inputs; **L** estimate to be replaced by a T-109/T-111 measurement. Where an input is project data it is cited as `[P#]`.
- **Method note.** Web access was used for prior art and API behaviour; hardware and engine numbers that no source gave are derived from the project's own M1 measurements (M-018, M-015) and marked **L**. Nothing here lowers any gate.

## Headline

1. **IO is not the constraint; main-thread work, collider cooking and memory churn are.** A 75 km pass at the 60 m/s stress speed needs about 6 MB/s of tile reads and about 0.6 core-seconds per second of tile build (section 1). Any SSD gives 100x headroom [14][15]. The M1 per-tile build (mean 2.09 s on the main thread, 15 tiles [P4]) is what must move off the main thread and be sliced.
2. **Select LOD by projected error in output pixels with threshold tau = 1/k output px** (k = integer upscale, 4 at 1080p). This is not a taste value: it is what a 1 px RMS silhouette gate (M-102) implies once the internal grid quantises silhouettes (section 2). Switch distance is then `d = error_m x 1158 x k` metres for vFOV 50 deg and 1080 rows (4632 m per metre of error at k = 4).
3. **Visibility is haze-limited, so streaming radius is set by the palette profile.** Geometry beyond the Koschmieder visual range V (transmittance 2 %) is invisible; beyond 0.63 V it falls into the last single-tone band. Default V 30 km gives a render ring of 30 km, which terrain at L4 and building impostors cover with ~16 coarse tiles. Salesforce (326 m) is still 3.1 internal texels tall at 30 km, so towers get a skyline-impostor exception out to V (section 3).
4. **Physics ring = 512 m around every physics body, in 256 m chunks, not whole tiles;** design speed 30 m/s, hard cap 60 m/s (section 5). Per-building GameObjects and colliders exist only inside this ring (the M1 builder makes one per building for the whole tile).
5. **Origin management is per cluster, not global.** Bodies are grouped into activity clusters of Chebyshev extent <= 5120 m; each cluster has a tile-corner origin and (host) its own `PhysicsScene`. A single global origin cannot hold two bodies 50 km apart (section 6).
6. **Destruction persists as a per-tile journal** (removed building IDs as a set, terrain edits as an ordered op list), applied while the tile is built, and re-applied to LOD forms through per-building index ranges (section 7).

## 2. LOD selection in output pixels for a pixel-art renderer

**Projection (M, H).** With output height H_out rows and vertical FOV f, an object of size e metres at distance d spans `e x H_out / (2 d tan(f/2))` output pixels. For H_out = 1080, f = 50 deg (R-003 [P2]): **1158 / d output px per metre** (289.5 / d internal texels at k = 4; 231.6 / d at k = 5).

**Why the threshold is in output pixels and equals 1/k.** The world is drawn into an RT of internal pixels and upscaled by integer k with the silhouette snapped to texels [P2 sec 2]. A geometric displacement e_out (output px) of a silhouette moves a texel edge only if the shift crosses a texel boundary; for a random sub-texel phase that happens with probability p = e_out / k (e_out < k), and when it happens the contour moves by k output px. The RMS contour displacement is `sqrt(p) x k = sqrt(k x e_out)` output px. The M-102 gate (RMS silhouette <= 1 px, plan text [P-plan Track 2]) therefore requires

`e_out <= 1/k`  (k = 4: 0.25 output px = 0.0625 internal texel; k = 5: 0.2 px; k = 6: 0.167 px).

The ΔE clause (<= 2.0 on >= 99 % of pixels) is looser: changed pixels are silhouette texels, share = edge share x p; with an edge share <= 10 % it allows p <= 0.1, so the RMS clause binds. Interior pixels do not change when geometry error is small because colour comes from the same albedo field, not from the mesh (the terrain albedo, including road decals, is baked; `WorldGeo.json` ramps [P9]).

**Selection rule (proposal).** For a candidate tile or chunk at level n with baked errors (section 8): `e_out = err_rms_m[n] x 1158 / d_min`, where d_min is the distance from the camera to the closest point of the chunk AABB (conservative), taken as the maximum over all active cameras (as cesium-native does over views [2]). Select the coarsest level with `e_out <= tau`, tau = 1/k at the active integer scale; guard `err_max_m` with `err_max x 1158 / d_min <= 4 tau` so a single outlier vertex cannot pass. The same function runs engine-free in `World.Streaming` (priority input) and in the Unity selector.

**Switch distance** `d_n = err_rms_m[n] x 1158 x k` (k = 4: 4632 m per metre of error):

| err_rms of level (m) | 0.1 | 0.25 | 0.5 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|---|---|---|
| d at k = 4 (km) | 0.46 | 1.16 | 2.3 | 4.6 | 9.3 | 18.5 | 37 |
| d at k = 6 (km) | 0.69 | 1.7 | 3.5 | 6.9 | 13.9 | 27.8 | 55.6 |

The errors are not yet measured (the `bake_lod.py` table is the source). Planning default: terrain error ladder 0.1 x 2^n m for the 2^n x decimated surface (flat urban terrain is better than the ladder, ridges worse), which gives L1 from 0.93 km, L2 from 1.9 km, L3 from 3.7 km, L4 from 7.4 km at k = 4. At k = 6 (4K, Q-NEW-b of R-003) every distance grows by 1.5, so **the ring radii must be computed from k at runtime, never hard-coded**.

**What this implies for buildings (M).** A building LOD whose only error is footprint simplification of 2 m would have to wait until 9.3 km (k = 4); that is infeasible for triangle count (an urban L0 tile is about 1.1 M triangles, so a 9 km disc of SF and Oakland is about 100 tiles). The way out stays inside the gate:
- **B0 (L0 chunk, lossless):** merge draw calls only. Per-building GameObjects exist only in the physics ring.
- **B1 merged block (lossless in silhouette):** exact tops and exact outer footprint vertices, remove interior faces, courtyards, wall skirts and sub-pixel parts; footprint simplification <= `tau x d / 1158` at the *switch* distance (0.2 m at 0.9 km, 1 m at 4.6 km).
- **B2 skyline impostor:** one watertight prism per tall building (height >= 60 m) and max-pooled rooftop surface elsewhere; exact height, footprint simplified to the switch-distance error.
- The vertical error of merged forms is zero by construction (heights preserved, max-pooled, never averaged), which matters because skyline distance is dominated by height.

**Popping and shimmer under the pixel pipeline (M-004).**
1. **Terrain: geomorph.** Every pyramid vertex stores its parent height; the vertex shader blends fine to coarse over a morph band (last 30 % before the switch). Because the switch happens where the error is <= tau, the morph moves silhouettes by < tau, below one texel on average. RTIN meshes are natural for this (each split vertex has a parent); LOD0 to L1 continuity is exact at shared lattice nodes (`GeoEdgePolicy` [P9]).
2. **Buildings and props: dithered cross-fade.** URP 17 supports LOD cross-fade with Bayer, blue noise or stencil dithering (`LODCrossFadeDitheringType`) and the LOD Group fade modes; standard URP materials do not dither, custom shaders must read the LOD fade value [9][10]. Use the **Bayer** mode and the pipeline's own Bayer origin (anchored to the rotation-quantised frame, R-003 sec 7 [P2]) so the fade pattern is the same pattern the quantiser dithers with, and so a fade shows as ordered dither, not alpha blending (no off-palette pixels).
3. **Time-based fade, 0.6 s (36 frames at 60 fps)**, started when the selector crosses the switch distance and never reversed mid-fade (hysteresis, below). Changed texels per frame are then a small fraction of one fade, not an on/off flip.
4. **Hysteresis.** Switch up at `d_n x 1.0`, down at `d_n x 1.15` (about 10 to 15 %). Prevents flicker near the distance when the camera dithers around it, which is exactly the < 1 texel/frame regime where R-003 sees visible stepping [P2 sec 7].
5. **Same albedo and same shading inputs at every level.** Level n+1 may use a normal-map-free simplified normal, but the terrain colour ramp keys on height and slope sampled from the L0 field baked into the level (`slope_q` channel), otherwise ΔE changes with level.
6. **No LOD change on the rotation-quantisation step.** The selector is evaluated at the position-snapped camera (R-003 `d_ref` snapping) so that LOD does not depend on sub-texel camera motion.
7. **Sky and far plane.** Anything past `D_cut` (section 3) fades into the last band through the haze shader, not through culling; fade by haze, cull when `T < 0.02`.

## 3. Haze-limited visibility and the skyline

**Inputs (H from R-003 sec 5 [P2]).** `T(d) = exp(-beta d)`, Koschmieder visual range `V = 3.912 / beta` (T = 0.02). Six transmittance bands: band edges `d_i = -ln(1 - i/6) / beta`; the last band (index 5) starts at `ln 6 / beta = 0.458 V`. R-003 assumes V of 15 to 30 km for the stylised look and clear Bay air at tens of km; the profile (`PaletteProfile`) owns V. The camera is at 100 to 300 m, so the scale-height factor `exp(-h/1.2 km)` is 0.8 to 0.92 (a hill top at 280 m shortens the effective density by 20 %); I ignore it for rings and keep it in the shader.

**Streaming radii as functions of V (M):**

| Quantity | Definition | V = 15 km | V = 30 km | V = 60 km |
|---|---|---|---|---|
| Last band begins | `0.458 V` | 6.9 km | 13.7 km | 27.5 km |
| Last-band colours indistinguishable from sky (T < 1/12, half a band) | `ln 12 / beta = 0.635 V` | 9.5 km | 19.1 km | 38.1 km |
| **`D_cut`** hard cull (T = 0.02) | `V` | 15 km | 30 km | 60 km |
| L0 (3 x 3) share of `D_cut` | | 10 % | 5 % | 2.5 % |

**Rules.** (a) The render ring radius is `D_cut = clamp(V of the active profile, 15 km, 60 km)`; terrain at L3 and L4 (and B2 forms) fill it. (b) Between `0.635 V` and `V` only terrain silhouettes and the skyline exception are drawn, in the last band's two palette colours. (c) The profile V changes with district and time of day, so `D_cut` changes at runtime; shrinking `D_cut` frees tiles, growing it needs prefetch (use the profile's *maximum* over the next 60 s of the schedule).

**Skyline visibility (M).** A tower of height h at distance d spans `h x 289.5 / d` internal texels at k = 4 (480 x 270). Salesforce, 326 m tall [P9, Landmarks] subtends 3.1 texels at 30 km, 1 texel at 94 km: geometry is never the limit, haze is. Contrast through haze `C = C0 T`: at 30 km with V = 30 km, T = 0.02, so the tower is gone, while at V = 60 km it is 6.4 texels tall and still has T = 0.14 (one band above sky). Hence:
- Skyline exception: any building with height >= 150 m, Sutro Tower and the Golden Gate towers (listed in `landmarks.json`) stay in B2 form out to `D_cut` regardless of their L-tile; cost is a handful of prisms (R-004 lists 8+ landmarks with sourced heights [P1 sec 5]).
- Terrain relief (Mt Tamalpais 784 m, Mt Diablo 1173 m, Mt Hamilton 1281 m, R-004 DEM extents) is carried by L4 tiles, which also tolerate the largest error (8 m at 37 km = 1 px).
- Earth curvature at 30 km drops a target by `d^2/2R` = 70 m (63 m with 7/6 refraction; R-003 flagged this for R-004 [P2 sec 5]); at 75 km it is 441 m. BayTM is a projected plane, so curvature is absent. Visually negligible inside 10 km (7.8 m). Proposal: a render-only vertex bend, **default off** (`world.streaming.curvature`, Q-NEW), re-judged by the style evaluator.

**Why node subsample, not area average, for terrain.** Shared edges stay identical between neighbours at every level (R-004 seam rule [P1 sec 3.1], `GeoEdgePolicy` [P9]); shorelines keep their datum (averaging pulls a pier or seawall into the water); averaging lowers ridges and the skyline. Max-pool for B2 rooftops, node subsample for terrain.

**Mesh vs impostor.** Billboard impostors do not work at Bay scale: they shimmer under rotation quantisation (R-003 sec 7 [P2]) and need per-view atlases. Merged 3D blocks keep exact tops, move with perspective and are covered by the same haze and quantiser. Billboards are retained only for the 2 to 5 smallest sub-texel clusters of far, small buildings (none planned).

**Landmarks.** The Golden Gate deck and cables are already cut at 40 m with shared nodes [P9]; LOD form: deck 120 m segments, cables as lines of capsules, towers exact. Landmark colliders only inside the physics ring.

## 5. Physics and collider ring vs the fastest body

**Latency model.** A chunk collider must exist before a body can touch it: `R_phys >= reach + v x (t_lat + t_margin)`, where `reach` = body reach beyond its centre (kaiju 80 m; mech arm 40 m; take **100 m**), `t_lat` = p99 time from the chunk entering the prefetch radius to a cooked collider (target 1.5 s), `t_margin` = 1.0 s.

| v | 30 m/s (design) | 60 m/s (cap) |
|---|---|---|
| `R_phys` (M) | 100 + 30 x 2.5 = **175 m** | 100 + 60 x 2.5 = 250 m |

**Decision: `R_phys` = 512 m in 256 m chunks (2 chunks of margin), evict at 768 m (hysteresis).** 512 m covers the cap with 2 x margin and equals two M1 chunk widths, so the ring is chunk-aligned: 17 x 17 = 289 chunks at most per body, in practice <= 40 for a single body (only chunks with colliders within 512 m of the body's AABB centre).

**Invariants (testable in T-107/T-109):**
1. **Physics hold.** A body whose ring is not fully resident is set kinematic-frozen (velocity kept in a side slot) and released when it is; it never falls through. Hold events are counted and must be zero in M-015@v2 for bodies at <= 30 m/s.
2. **CCD only where needed.** Mech/kaiju segments are large and slow compared with the collision margin; large bodies at < 60 m/s with 0.1 m contact offset (R5 in R-005 [P-R005 table row R5]) move 1.2 m per 0.02 s step at the cap; Unity's current guidance prefers *Continuous Speculative* for CCD and cautions that *Continuous Dynamic* has the highest CPU cost [11]. Debris and projectiles use speculative CCD; the mech/kaiju links keep what T-005 decides.
3. **Terrain collider granularity.** The M1 builder uses one full-resolution `TerrainCollider` per tile (2049^2 heights). Building that on the main thread is not sliceable. Default for T-109: split into 512 m terrain blocks with `heightmapResolution` 513 (0.5 M samples, 1 MB each) built from the already-decoded array, one per frame at most; fallback if blocks are too slow: chunk `MeshCollider` via `Physics.BakeMesh` in jobs [6]. T-109 step 0 microbenchmarks both (Open question O4).
4. **Debris.** Debris outside the ring is despawned and its mass becomes a static decal (no collider); debris never lengthens `R_phys`.
5. **Non-default `PhysicsScene`.** A scene other than the default is not simulated automatically; call `PhysicsScene.Simulate` each fixed step [8].

## 6. Floating origin at Bay scale with many bodies

**State of the code (M1, [P9]).** Origin = tile corner; rebase when |p| > 3072 m on either axis (`DefaultRebaseDistanceM`); roots shift by exact integers; neighbouring geometry stays within about 5120 m (float32 ulp about 1 mm there); M-015 evidence is a proxy route, 0.121 mm round trip, 0.244 mm ulp at 2048 to 4096 m [P5].

**Bound arithmetic (M).** Ulp is 0.24 mm in [2048, 4096) m and 0.49 mm in [4096, 8192) m [P1 sec 2.4]. M-015@v2 asks for every body <= 4096 m.

**Clusters.**
- Each simulated body belongs to one **activity cluster**. Two bodies are linked when their Chebyshev distance is < 3072 m and the merged AABB extent stays <= 5120 m; clusters split when extent exceeds 5120 m.
- A cluster's origin O is the tile corner nearest its AABB centre. Corner snapping can offset by up to 1024 m, so a body is within `extent/2 + 1024` = 3584 m of O, **inside 4096 m with 512 m to spare**; the extent cap 6144 m would exactly reach 4096 m, which is why 5120 m is chosen.
- Rebase when any body in the cluster exceeds 3072 m (M1 value; R-004's earlier suggestion of 1024 m is sufficient but costs more rebases). Slack to the 4096 m bound is 1024 m = 17 s at 60 m/s, 34 s at 30 m/s: schedule the rebase to a quiet fixed step; force it at 3840 m.
- **Host:** one `PhysicsScene` per cluster (fixed-step called manually [8]); with mechs and kaiju in the same battle this is one cluster, usually. **Clients:** one render origin per client camera. Bodies in other clusters are render proxies at float32 offsets from the client's origin (ulp 7.8 mm at 65 to 131 km [P1]) because anything beyond `D_cut` is not drawn and nothing there is simulated locally. This matches R-004's two options (a `PhysicsScene` per activity region, or bounded separation) and chooses the first, because the two-process co-op of T-030c already has separate processes per player.
- **Authoritative state is float64.** `world = O + local` is recomputed, never integrated in float32. Rebase = subtract an exact integer multiple of 2048 from all local float32 positions (exact), shift tile roots (not their 1000s of children), call `Physics.SyncTransforms` once.

**Cost of a rebase (L).** Static colliders under a moved root are re-synced by PhysX; with per-building colliders limited to the 512 m ring this is <= a few hundred shapes, but T-109 must measure (M-101 counts a rebase frame as a streaming frame).

**Many bodies.** Debris is the stressor: at 4 GJ fall energy (about 1 t TNT [P6]) a collapse can spawn hundreds of fragments. Rules: pooled bodies, at most 256 dynamic debris per cluster, positions in the cluster's local frame, retired when outside `R_phys` of any body or after a lifetime.

**Render side.** Each tile root also keeps `ShiftOrigin`; the pixel pipeline's texel snapping works on camera-relative coordinates so a rebase must not change the snapped phase: rebase shifts by whole tile multiples (2048 m = integer texels at every k only if the texel size divides 2048 m; it does not in general), so the **camera snapping grid is expressed in BayTM float64**, not in local space (a requirement on the Pixel module, flagged as O9).

## 7. Destruction persistence for unloaded tiles (F-043)

- **State to keep, per L0 tile (M).** (a) The **set** of removed `BuildingId`s (order-free, idempotent); (b) an **ordered journal** of terrain edit ops (crater centre float64, radius, depth, seed); (c) optional per-building damage records from `IDamageModel` (kept by Destruction, referenced by ID). Worst case: 5 x 10^5 buildings x 4 B = 2 MB for the whole Bay destroyed (SF alone about 150 k buildings is **L**); journals are per event, kilobytes.
- **Where.** New save section `streaming@v1` holds only the per-tile journals (tile ID to sorted ID list and op list); `destruction@v1` (not read by this note; T-110 to confirm) stays the authority for per-building damage state. Alternative: extend `destruction@v1` with a per-tile index; rejected as default because a streaming journal must exist even when the destruction module is off.
- **Eviction.** `TileEvicted` carries IDs only; the Unity side flushes the tile's journal to the `streaming@v1` store before releasing meshes (journal updated at removal time, not at eviction, so a crash loses nothing).
- **Reload.** The tile builder receives the removed set and **omits those buildings before meshing and before collider cooking** (cheaper than build-then-remove); terrain ops replay in order after the heights decode and before RTIN, so the crater is in the mesh. Terrain edits apply to a pyramid level only when `depth >= err_max[n]`.
- **LOD forms.** B1/B2 chunks keep per-building index ranges sorted by `bid`; the builder drops the ranges of removed buildings (no re-bake). A removal while a coarse form is visible rebuilds that one 256 m chunk of the active level off-thread, as the L0 chunk rebuild does today [P9 `RemoveBuilding`].
- **Determinism.** Same removed set and ops give byte-identical meshes (tests in T-107 with the engine-free builder).
- **Not persisted.** Dynamic debris and fires; they become static decals or vanish at eviction.

## 8. Proposed contracts

### 8.1 `World.Streaming` (L2, engine-free, `Game.World.Streaming`; references `Game.Core` and `Game.World.Geo.Contracts`)

```csharp
public enum FocusKind : byte { Camera, Body }
public struct FocusSample {                // sampled once per tick; double world position (BayTM, NAVD88 y)
  public int Id;                           // stable per focus
  public FocusKind Kind;
  public double X, Y, Z;  public float Vx, Vy, Vz;
  public float ReachM;                     // body reach (physics ring margin)
  public float FovDeg; public int OutputHeightPx; public int IntegerScale;   // cameras only
  public float VisualRangeM;               // active haze profile V (D_cut = clamp(V,15000,60000))
}
public interface IStreamingFocus { int Fill(Span<FocusSample> buffer); }      // cameras, mechs, kaiju (+ remote proxies flagged Kind=Camera with their own V)

public enum ResidencyKind : byte { Render, Physics }
public struct TileResident : IEvent { public GeoTileId Tile; public ResidencyKind Kind; public int Generation; }  // unmanaged, IDs only
public struct TileEvicted  : IEvent { public GeoTileId Tile; public ResidencyKind Kind; public int Generation; }

public struct StreamingBudget {            // all enforced by the scheduler, never exceeded
  public long GpuBytes, CpuBytes;          // defaults 1.5 GB / 350 MB
  public int MaxInFlightReads;             // 4
  public float MainThreadSliceMs;          // 2.0; single work item <= 4.0
  public int MaxPhysicsChunks;             // 600
}
public struct RingSpec { public int Level; public float RadiusM; public float HysteresisFrac; public bool Physics; }  // physics ring is chunk-level, radius 512 m, evict at 768 m
public interface IStreamingScheduler {
  void Tick(double dt, ReadOnlySpan<FocusSample> foci, StreamingPlan plan);     // deterministic, no allocation after warm-up
  TileState GetState(GeoTileId tile);      // Absent, Requested, Reading, Building, Resident, Evicting
  void Completed(GeoTileId tile, ResidencyKind kind, long gpuBytes, long cpuBytes);   // Unity side reports; fires TileResident
  void Failed(GeoTileId tile, string reason);                                    // retry with backoff, then park
}
public sealed class StreamingPlan { public readonly List<TileRequest> Load; public readonly List<GeoTileId> Evict; }
```

**Residency rules (all tested engine-free):**
1. Tile quadtree: an L(n) tile has four L(n-1) children (same indexing as `GeoTileId`, `I`/`J` halve per level).
2. A tile is **wanted** if, for any focus, `SSE(tile) > tau` of its parent (refine) and its distance <= ring radius, or it lies in the physics ring (chunks). Coverage is REPLACE-style with **parent fallback**: a parent is never evicted until all wanted children are resident (no holes, as 3D Tiles REPLACE [1][2]).
3. **Priority** (higher loads first): `P = (1 + min(8, sse/tau)) / (t_reach + 0.25)`, with `t_reach = max(0, d_min - R_ring) / max(v_closing, 1 m/s)` over all foci; tiles needed by the physics ring get `P x 1000` (always first; they are the only requests allowed to preempt the main-thread slice). Ties break on `GeoTileId` order (determinism).
4. **Prefetch lead** = `v x t_lat` with `t_lat` = 4 s default (so at 60 m/s the L0 ring boundary is requested 240 m early; the 1.5 km radius covers it).
5. **Eviction:** order by (not needed by any focus) then lowest P then LRU; never a physics-ring tile, never a parent with a wanted child; when over budget evict until under 90 %.
6. **Hysteresis:** unload at radius x 1.25 (render) / 768 m (physics); level switch at 1.0 up and 1.15 down (section 2).
7. The scheduler never sees Unity types; it consumes `IStreamingFocus` and a `ITileCostModel` (bytes per tile from the manifest, `geo_lod@v1` `stats`).
8. Flag `world.streaming` (default off). With it off, M1 `GeoTileSetBuilder` behaviour is unchanged.

### 8.2 `geo_lod@v1` data spec (Pipelines/geo, `bake_lod.py`)

Location: `Pipelines/geo/cache/tiles/v1/L{L}/{i}_{j}/` for L = 1..4 (same layout as `geo_tile@v1`, level folder already reserved by R-004 sec 3.1 [P1]); L0 stays `geo_tile@v1`. Deterministic: two runs byte-identical per manifest fingerprint (as T-102).

```json
  "licence_ok": true }
```

- **`.lodmesh` (binary, little-endian):** header (magic `KLOD`, version 1, vertex count, index count, chunk table), positions as uint16 quantised to the chunk AABB (3.9 mm at 256 m chunks, below any LOD error), normals oct-encoded 2 x int8, 16-bit indices per chunk, **per-building index ranges** `(bid_u32 or id string table index, first_index, count)` sorted by `bid` for removal (section 7).
- **`b*.index.json`** lists for every building: `bid`, chunk, min/max height, `landmark` flag.
- **Validator** (Python, in `kaiju_geo/manifest.py` style, mirrored by C#): refuses a level whose `source_fingerprint` does not match, whose errors are missing, or whose neighbours disagree on shared edge nodes (node subsample gives exact equality).
- **Versioning.** Any change to a field's meaning bumps to `geo_lod@v2`. `GeoContractVersions` gains `LodSpec = "geo_lod@v1"`.

### M-015@v2: floating-origin precision at Bay scale (supersedes M-015@v1)

- **Definition.** During a streamed traversal of a path of >= 75.0 km (BayTM polyline Golden Gate to San Jose, computed in float64) with >= 2 mechs, >= 3 kaiju and >= 100 debris bodies simulated, for **every simulated body at every fixed step**: (a) `max(|x|, |y|, |z|)` of its Unity position <= 4096 m; (b) `|O + (double)local - world64| <= 1 mm`, where `world64` is the authoritative float64 state; (c) round trip: a kinematic probe driven out along the path and back to its start returns with BayTM position error <= 1 mm; (d) across each rebase, pairwise distance between all bodies and terrain raycast height vs `SampleTerrain` change by <= 1 mm and <= 0.1 m respectively (v1 measured 0.07 m [P5]); (e) zero physics-hold events and zero frames with a body > 0.5 m below the data surface.
- **Procedure.** `FlythroughHarness` (T-111) runs the cluster logic; simulated time may exceed wall time (a 60 m/s body needs 21 min of simulated time, kaiju at 9.12 m/s need 137 min; run the headless step faster than real time with rendering off, the 10-minute wall-clock of v1 does not apply to simulated time). Log per step `max|pos|`, rebase count, errors; JSON `m015_v2.json`.
- **Threshold.** (a) 4096 m, (b) 1 mm, (c) 1 mm, (d) 1 mm / 0.1 m, (e) 0. Thresholds as in the plan; none lowered.
- **Source.** R-004 sec 2.4, plan Track 2, T-021 evidence (0.121 mm round trip, 0.07 m raycast [P5]), this note sec 6.

### M-101: streaming hitch

- **Definition.** On the scripted 75 km flythrough (camera plus 2 mechs and 3 kaiju, with a destruction event every 5 km): (a) **zero frames > 33.3 ms** (any cause); (b) p99 frame time within the M-013 bound in force (relative on Mac: <= 1.25 x the p99 of a control run with all tiles pre-resident on the same path); (c) *diagnostic:* main-thread `Streaming.*` marker time p99 <= 2.0 ms per frame and max <= 4.0 ms per work item; (d) zero **late tiles** (a frame where the wanted render level is not resident and the parent fallback is shown more than 2 s, or a physics hold); (e) draw calls per frame <= 2446 (the M-018 SoMa maximum) [P4].
- **Procedure.** Two speeds: 30 m/s (design) and 60 m/s (cap). Per frame record frame time, `Draw Calls Count`, `SetPass Calls Count`, `Triangles Count` (R-006 sec 4 recorders [P3]), custom markers `Streaming.Read/Build/Apply/Cook/Rebase`. Control run identical but `world.streaming` pre-warm. Cold start with an empty OS file cache is also recorded (single run).
- **Threshold.** (a) 0 frames > 33.3 ms; (b) as above; (c), (d), (e) as above.
- **Source.** plan Track 2 (M-101 text), M-013/M-018, this note secs 1 and 5.

### M-102: LOD pixel error and no popping

- **Definition.** For every LOD switch (T1..T4, B1, B2) at its production switch distance `d_n`, comparing the output of level n with the L0 reference at the same pose, same pipeline settings and same snapped camera phase (`style_capture@v1`): (a) **RMS silhouette contour displacement <= 1.0 output px**, the contour taken from the depth-band index (sky vs non-sky and building-vs-terrain edge masks) at output resolution, bidirectional distance; (b) **CIEDE2000 <= 2.0 on >= 99 % of output pixels** (M-003 colour metric [P-M003]); (c) **no popping:** on a 240-frame camera sweep through each switch at 2, 10 and 30 m/s, with LOD enabled and with LOD pinned to L0, `M-004@v1` measures (S_px, C_px, F) of the LOD sequence must meet the M-004 translation thresholds and be <= the pinned run + 0.01 (S_px, C_px); and zero *pop events*, where a pop event is one frame in which the share of output pixels changed inside the mask of tiles whose level changed that frame exceeds `max(0.25 %, 3 x median of the previous 10 frames)`.
- **Procedure.** >= 12 viewpoints (GG, SoMa, Marin hills, shoreline, one skyline view from the east bay) x 3 yaws, at k = 4 and k = 6; forced level via a debug override `StreamingDebug.ForceLevel`; capture 2 frames per switch (just inside/outside, `d_n x 0.98 / 1.02`) plus the sweeps. Analysis in Python (`m102_check.py`), one JSON.
- **Threshold.** (a) <= 1.0 px, (b) >= 99 % at ΔE <= 2.0, (c) as above; plus a derived note: the RMS clause is equivalent to `e_out <= 1/k`, which sets the selection tau (section 2).
- **Source.** plan Track 2, M-003/M-004 (R-002), R-003 sec 7, this note sec 2.
