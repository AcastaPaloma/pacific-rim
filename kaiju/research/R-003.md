### 1.2 Minimal verified skeleton (one full-screen pass, swap-not-copy)
```csharp
using UnityEngine; using UnityEngine.Rendering; using UnityEngine.Rendering.Universal;
using UnityEngine.Rendering.RenderGraphModule;
public sealed class PixelStageFeature : ScriptableRendererFeature {
  public Material material; public RenderPassEvent injection = RenderPassEvent.AfterRenderingPostProcessing;
  public ScriptableRenderPassInput inputs = ScriptableRenderPassInput.Depth;
  StagePass m_Pass;
  public override void Create() => m_Pass = new StagePass { renderPassEvent = injection };
  public override void AddRenderPasses(ScriptableRenderer r, ref RenderingData rd) {
    var t = rd.cameraData.cameraType;
    if (material == null || t == CameraType.Preview || t == CameraType.Reflection) return;
    m_Pass.material = material; m_Pass.ConfigureInput(inputs); r.EnqueuePass(m_Pass);
  }
  sealed class StagePass : ScriptableRenderPass {
    public Material material;
    class Data { public TextureHandle src, dst; public Material mat; }
    public StagePass() { requiresIntermediateTexture = true; }   // never read the backbuffer
    public override void RecordRenderGraph(RenderGraph rg, ContextContainer fd) {
      var res = fd.Get<UniversalResourceData>();
      if (res.isActiveTargetBackBuffer) return;
      var desc = rg.GetTextureDesc(res.activeColorTexture);
      desc.name = "_PixelStage"; desc.clearBuffer = false; desc.msaaSamples = MSAASamples.None; desc.filterMode = FilterMode.Point;
      using var b = rg.AddRasterRenderPass<Data>("Pixel.Stage", out var d);
      d.src = res.activeColorTexture; d.dst = rg.CreateTexture(desc); d.mat = material;
      b.UseTexture(d.src);
      if ((input & ScriptableRenderPassInput.Depth) != 0) b.UseTexture(res.cameraDepthTexture);
      b.SetRenderAttachment(d.dst, 0, AccessFlags.WriteAll);
      b.SetRenderFunc(static (Data d, RasterGraphContext c) => {
        bool flip = c.GetTextureUVOrigin(d.src) != c.GetTextureUVOrigin(d.dst);
        Blitter.BlitTexture(c.cmd, d.src, flip ? new Vector4(1,-1,0,1) : new Vector4(1,1,0,0), d.mat, 0);
      });
      res.cameraColor = d.dst;                                     // next stage reads this
    }
  }
}
```
Shader: `#include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"`, `#include "Packages/com.unity.render-pipelines.core/Runtime/Utilities/Blit.hlsl"`, `#pragma vertex Vert`, sample `_BlitTexture` with `LOAD_TEXTURE2D_X(_BlitTexture, uint2(input.positionCS.xy))` (integer load: no filtering at the pixel grid), as in `URP/Samples~/URPRenderGraphSamples/BlitWithMaterial/BlitWithMaterial.shader`. Validate any real feature with the installed `unity:validate-urp-render-graph-renderer-feature` skill.

### 1.3 Configuring renderer assets from an Editor script (no text edits)
- Features are **sub-assets** of the `UniversalRendererData` asset, referenced by two parallel serialized lists `m_RendererFeatures` and `m_RendererFeatureMap` (local file IDs). URP's own editor does: `CreateInstance(type)`, `name = type.Name`, `hideFlags |= HideInHierarchy`, `AssetDatabase.AddObjectToAsset(component, rendererData)`, `TryGetGUIDAndLocalFileIdentifier(component, out _, out long localId)`, grow both lists through `SerializedObject`, `ApplyModifiedProperties()`, save (`URP/Editor/ScriptableRendererDataEditor.cs:63-66,270-306`). Our `Tools/Rendering/PixelPipelineInstaller` must do exactly this, then call `rendererData.SetDirty()` (public `new` method that invalidates the renderer, `URP/Runtime/ScriptableRendererData.cs:59`), `EditorUtility.SetDirty`, `AssetDatabase.SaveAssets()`. Appending to `rendererFeatures` alone leaves the map stale; `ValidateRendererFeatures()` then "re-maps" by guesswork (`ScriptableRendererData.cs:144-200`). Order in the list = execution order within the same `renderPassEvent` (queue index), so reordering = reordering both lists together.
- Toggling: `feature.SetActive(bool)` (serialized `m_Active`), driven from `Config/FeatureFlags` at startup; no asset edit needed at runtime.
- The pipeline asset's renderer list `m_RendererDataList` has only a read-only accessor `rendererDataList` (`URP/Runtime/Data/UniversalRenderPipelineAsset.cs:441,665`): add the second (present) renderer via `SerializedObject.FindProperty("m_RendererDataList")`; select it per camera with `UniversalAdditionalCameraData.SetRenderer(int)` (`URP/Runtime/UniversalAdditionalCameraData.cs:728`). `renderScale` is settable and clamped to [`minRenderScale` 0.1, `maxRenderScale` 3.0] (`UniversalRenderPipeline.cs:188-199`).
- Current project state (read, not changed): `Assets/Settings/PC_RPAsset.asset` has `m_RenderScale: 1`, `m_MSAA: 1`, `m_SupportsHDR: 1`, depth + opaque texture on; `PC_Renderer.asset` is Forward+ (`m_RenderingMode: 2`, enum in `URP/Runtime/UniversalRenderer.cs:11-22`) with an SSAO feature. Pixel renderers should be new assets, not edits of the template ones.

### 1.4 Pitfalls (each verified or flagged)
- **Descriptors:** `GetTextureDesc(activeColorTexture)` inherits MSAA samples and HDR format (B10G11R11 at 32-bit HDR precision: no alpha). Set `msaaSamples = None`, `clearBuffer = false`, `filterMode = Point`, and choose `GraphicsFormat` explicitly for index/LUT targets (H, `RenderGraphResourceTexture.cs:254-326`).
- **MSAA / AA:** turn MSAA, FXAA and TAA/STP off on the pixel camera: resolved edge colours and temporal blends are off-palette and smear one-texel features; STP also forces TAA on (`UniversalRenderPipeline.cs:1893-1902`). Anti-aliasing is replaced by the supersample-then-downsample stage (§7).
- **Camera stacking:** URP's own sample warns that swapping `cameraColor` is unsafe across stacked cameras (`BlitAndSwapColorRendererFeature.cs` comment; `UniversalRendererRenderGraph.cs:1474-1476` TODO). Use **no overlay cameras** on the pixel camera; HUD lives on the present camera.
- **Scene view:** render scale is forced to 1 for SceneView/Preview/Reflection cameras (`UniversalRenderPipeline.cs:1860-1867`), so a render-scale design shows a full-res Scene view. Skip Preview/Reflection in `AddRenderPasses`; optionally skip SceneView (`cameraData.isSceneViewCamera`) behind a debug flag.
- **HDR & colour space:** project is Linear (`ProjectSettings/ProjectSettings.asset m_ActiveColorSpace: 1`). Quantise after tonemapping, in sRGB-encoded coordinates. If a pass writes the backbuffer itself, replicate `requireSrgbConversion = targetTexture == null && Display.main.requiresSrgbBlitToBackbuffer` (internal in `UniversalCameraData.cs:276-287`; `Display.main.requiresSrgbBlitToBackbuffer` is public engine API).
- **y-flip:** use the `TextureUVOrigin` rule (fact 10); Metal and D3D share top-left origin, so a Mac-only test will not catch an OpenGL/Vulkan-on-Android flip, but our Windows D3D target behaves like Metal (H for the rule, M for the platform claim per `RenderingUtils.cs:885-889`).
- **Upscaler framework:** `IUpscaler`/`UpscalerRegistry` exist in CORE but are compiled only under `ENABLE_UPSCALER_FRAMEWORK` (`CORE/Runtime/Upscaling/IUpscaler.cs:1`, `Upscaling.cs:1`), which is **not** in this project's defines (`Library/Bee/artifacts/200b0aE.dag/Unity.RenderPipelines.Core.Runtime.rsp`, `…Universal.Runtime.rsp` list `UNITY_6000_6_OR_NEWER` but no such define). Do not build on it.
- **Batch-mode capture on macOS Metal:** the protocol already says not to pass `-nographics`. Batch mode does not present a swapchain; Unity has answered "batchmode does not do any rendering" for player-loop screen grabs [3], and Apple-silicon batch Play Mode tests have had Metal crashes [4]. Capture by explicit rendering: `RenderPipeline.SubmitRenderRequest(camera, new UniversalRenderPipeline.SingleCameraRequest{ destination = rt })` (`UniversalRenderPipeline.cs:902,2957`) or `camera.Render()` into a `RenderTexture`, then `AsyncGPUReadback`/`ReadPixels`. The dedicated low-res RT design (§2) makes this trivial: read the internal-res palette RT directly (M). **First pixel task must smoke-test one capture in batch mode on the Mac** (L).
- **Apple TBDR vs Windows IMR:** raster passes may be merged into native render passes on Metal; unsafe/material-blit passes break merging. Irrelevant at ~130 k pixels, but profile on Windows separately (M).

## 3. Palette quantisation

Evidence from our refs (kaiju env, `scikit-learn` k-means in CIELAB on 60 k sampled pixels; script in scratchpad, reproducible): share of pixels within ΔE76 ≤ 10 of the nearest centre — k=16: 0.96 / 0.97 / 0.99 / 0.98 / 0.85 (refs 01,03,04,05,06); k=24: 0.99/0.98/0.99/0.99/0.90; k=32: ≥0.93 all. The refs are resampled JPEG-like images (158 k–279 k unique colours each), so tolerance-based M-003 is right; **16–24 colours per district profile** reproduces them. Note: `ref_01.png` and `ref_02.png` are byte-identical (md5 `c65df362…`), so the ref set has 5 distinct images.

| Approach | Mechanism | Lighting interaction | Look | Cost |
|---|---|---|---|---|
| Nearest-palette 3D LUT | precomputed `N³` table maps colour → palette index | lit gradients posterise into the nearest colours; a dark red may snap to a neighbouring brown (hue jumps) | crisp, can look "filtered photo" | 1 tex fetch |
| Ramp-based | luminance → step on a per-hue-family ramp (hand-picked dark-to-light) | preserves hue identity under shadow; value bands read as painted | most painted | small ALU or a 2D ramp LUT |
| Per-material palette | material outputs (ramp id, shade) or palette index directly | full art control; lighting must be quantised in the material | best on hero assets | authoring per material; breaks with standard Lit |

**Recommendation (M):** one runtime representation (point-sampled 3D LUT), two **offline** generation strategies chosen per `PaletteProfile`: (1) *nearest* in OKLab [5] (Euclidean, hue-linear, better than RGB for mixes), (2) *ramp-constrained*: each LUT cell is first assigned a hue family (OKLab hue/chroma sector of the profile's ramps), then the nearest step of that ramp by lightness. Size **32³** (cell = 8/255 in sRGB; 128 KB at RGBA8, `64³` = 1 MB brings nothing for ≤32 colours whose ΔE spacing is ≫ one cell). LUT coordinates = `LinearToSRGB(saturate(c))`, sampled with `Load` (no filtering). Channels: R = index a, G = index b, B = mix ratio t (for §4), A = reserved. Build in an Editor tool (Burst job or compute) from `PaletteProfile`; one slice per haze band (§5) stacked in a `Texture3D` of `32×32×32·(B+1)`. Because every output texel *is* a palette colour, M-003's "share within palette ΔE tolerance ≥ 95%" is met at 100% of world pixels by construction; the "painted" quality comes from ramp-constrained generation, value banding before quantisation (exposure/contrast curve in the profile) and haze bands. R-002 already publishes palettes as `palette_set@v1` with CIEDE2000 (`research/R-002/palettes.json`); `PaletteProfile` should import that schema; measure M-003 in CIEDE2000 as R-002 does, map in OKLab (the choice is irrelevant to the score since output ΔE = 0).

Lighting: keep URP Lit, but (a) clamp HDR with a fixed exposure + Neutral tonemap per profile so the quantiser sees a stable range, (b) prefer few strong lights (sun + emissive fire) so posterised bands are large, (c) disable SSAO in the pixel renderer initially (its soft gradients become dither noise) — evaluate later.

## 4. Ordered dithering

- **Where:** inside the quantise pass, **between the two best palette candidates**, not as noise added before a nearest lookup. Precompute per LUT cell the pair (a, b) and ratio t ∈ {0, 1/16, …, 1} minimising `ΔE_OK(mixLinear(a,b,t), c) + λ·ΔE_OK(a,b)` — Yliluoma's algorithm 1 with its penalty against mixing distant colours, mixing in linear light [6]. Runtime: `index = (bayer(x,y) < t) ? b : a`. One fetch, exact palette output, no off-palette pixels. Classic additive pre-dither (`c += s·(bayer−½)` then nearest) is the simpler fallback and works with any quantiser (keep it as `DitherMode.PreOffset`).
- **Matrix:** Bayer [7] 4×4 default (17 levels, reads as the hatch seen in the refs); 8×8 option for sky gradients; Yliluoma reports gains stop at 8×8–16×16 [6]. Blue noise survives scaling/video better [8] but reads less "pixel-art"; offer as a profile option.
- **Anchoring:** screen space at the internal resolution, but with the pattern origin owned by the camera rig: (1) translation — the pattern lives in the snapped low-res image, so it moves with the texel grid and the present shift (§7); (2) rotation — offset the pattern by the integer texel steps of quantised yaw/pitch so it follows the world near the screen centre, the cheap analogue of Obra Dinn's camera-sphere mapping, which Pope found best for rotation [8][9]; residual drift grows toward the edges by `1/cos²θ` (1.69× at the 16:9 edge for 50° vertical FOV, derived). Full sphere/cube mapping (pattern indexed by view direction) is a later experiment for the sky only, where it is exact (sky is at infinity) and has no parallax; Pope reports hand-tuning and cube-corner warps [8][9].
- **World/object-anchored patterns** (triplanar Bayer) stick to surfaces under translation but alias into moiré once a pattern cell is smaller than a texel (≥ a few hundred metres away at 3–5 mrad/texel), so use them only for near hero surfaces if ever (M).
- **Smoke/cloud edges:** particles write coverage, not blended colour: `clip(alpha − bayer(x,y))` ("screen-door") at internal res gives the clustered masses with dithered edges and no off-palette blends; density from soft particles/noise thresholded into 2–3 levels, then the quantiser maps colour (M; standard screen-door transparency).

## 5. Depth-based haze bands (aerial perspective)

**Physics (H/M).** Beer–Lambert transmittance `T(d) = exp(−β·d)`; observed colour `L = L₀·T + A·(1−T)` with airlight A (Koschmieder/Duntley). Koschmieder visual range `V = 3.912/β` (2% contrast) [10]; international haze class is 2–5 km, fog < 1 km [10]. With height, aerosol density falls as `exp(−h/H)`, `H ≈ 1.2 km` (Mie scale height used by Bruneton and Hillaire [11][12]); optical depth along a ray from height `h₀` to `h₁` over distance d: `τ = β₀·d·e^{−h₀/H}·(1−e^{−Δh/H})/(Δh/H)` (Δh→0 gives `β₀·d·e^{−h₀/H}`). Distance must be **radial**: `d = LinearEyeDepth(raw, _ZBufferParams) / dot(rayDir, camForward)` (`CORE/ShaderLibrary/Common.hlsl:1206`; or `ComputeWorldSpacePosition`, `:1399`). Earth curvature drops a target 196 m below the tangent plane at 50 km (`d²/2R`, derived) — a World/Streaming concern, flagged for R-004.

**Banding (derivation).** Posterise **transmittance**, not distance: N bands at equal steps of T give equal visual-contrast steps, edges at `d_i = −ln(1 − i/N)/β`. For N = 6:

| Visual range V (β) | band edges (km) | T at 50 km |
|---|---|---|
| 15 km (2.61e-4 /m) | 0.70, 1.55, 2.66, 4.21, 6.87 | ≈ 0 |
| 30 km (1.30e-4 /m) | 1.40, 3.11, 5.32, 8.42, 13.74 | 0.0015 |
| 60 km (6.52e-5 /m) | 2.80, 6.22, 10.63, 16.85, 27.48 | 0.038 |

So the mech/kaiju fight (< 1 km) sits in band 0 (darkest, full contrast, per §9 "near layers are darkest"), the Bay and far shore occupy bands 2–5, and beyond ~15–30 km everything merges into the sky band. `PaletteProfile` sets V (or β₀, H) per district/time: physically plausible values for clear Bay air are tens of km; the refs' look implies a short stylised V (≈ 10–20 km) — Assumed, pending calibration by the style evaluator. Bands always follow real distance, which keeps M-003's "value banding by depth is monotonic" true by construction.

**Per-band palette.** Each band b has its own LUT slice built from the profile palette pushed toward the airlight colour: `p_b = mixOK(p, A, 1 − T_b)` and re-snapped to the profile's allowed band colours (fewer, lighter, lower-contrast colours per far band: e.g. 12 / 8 / 6 / 4 / 3 / 2). **Transitions:** band index `= floor(N(1−T) + w·(bayer − ½))` with transition width w ≈ 0.5–1 band: dithered seams instead of hard contour lines. **Sky:** raw depth at the far plane (reversed-Z: 0) → sky band; sky colour from a per-profile gradient over elevation angle, posterised into 4–8 steps with the same Bayer seam rule (ordered dithering in sky, §9); horizon colour = A so far terrain melts into it. Transparent VFX (smoke) do not write depth: apply the same haze function in their shaders via a shared `PixelHaze.hlsl` include so haze is consistent.

Inject at `AfterRenderingSkybox` (400) or `BeforeRenderingPostProcessing` (550) in linear HDR colour (haze before tonemapping keeps the physical mix); the band index goes to a separate `R8_UNorm` texture published with `builder.SetGlobalTextureAfterPass(h, id)` (do not rely on colour alpha surviving URP post or the B10G11R11 HDR format) for the quantiser to pick the LUT slice.
