# R-023: host-authoritative co-op netcode (M1 Track 3)

Requirement F-063 (verbatim): "Host-authoritative online co-op over Steam; N player slots."
Scope: netcode stack for Unity 6.6 + Steam, sync model for slow heavy bodies, intent path, handshake, M-055..M-057 drafts, one-process two-peer testing.
Marking: figures with a URL are sourced; everything else is *Assumed*. Nothing here was run; no Unity was opened.

## 1. Summary

- **Recommendation (Q-101): a thin custom `Net` layer (engine-free, over `ITransport`) with a Steam adapter on Steam Networking Sockets via Facepunch.Steamworks.** It matches the Track 3 plan (`ITransport`, `SessionHandshake@v1`, `IntentPacket@v1`, `StateSnapshot@v1` keyed by `EntityId`, dotnet tests). It **deviates from STACK.md**, which names "Netcode for GameObjects + Steamworks transport". The founder must accept that change (Q-NEW-a).
- No option is blocked: all three can carry a host-authoritative session over Steam, so the stop condition does not trigger. The difference is who writes and maintains the Steam transport.
- Sync: snapshot interpolation, no client prediction for remote bodies, 100 ms base buffer at 20 Hz snapshots, pixel-snap after interpolation (section 3).
- Draft thresholds (all *Assumed*, to be ratified): M-055 p95 <= RTT/2 + 34 ms; M-056 p95 <= 1 px, max <= 2 px; M-057 <= 64 kB/s down per client at N=4.

## 3. Sync model for very slow, heavy bodies

**Choice: snapshot interpolation (no client prediction) for every remote body; the host is the only simulator.** Reasoning:
- Prediction pays when a player's own input must move their body within one frame (shooters). For a body whose peak acceleration is far below human scale (*Assumed*; no value is given in the files read), the response to an input over 100-150 ms is a displacement of 1/2*a*t^2; with *Assumed* a = 1 m/s^2 and t = 0.15 s that is 1.1 cm. Delay is therefore invisible; the cost of prediction (rollback, reconcile code, divergence bugs) is not justified.
- A body that is slow and smooth interpolates and extrapolates with tiny error, so a longer buffer costs little. Error of constant-velocity extrapolation over t is at most 1/2*a_max*t^2 (kinematics, no source needed).

**Parameters (all *Assumed* unless cited):**
- Snapshot rate 20 Hz = every 3rd Core step at 1/60 s (R-005 recommended step; Core config currently 0.02 s, so every 2.5th: pick the rate as a whole multiple of `fixedStepSeconds`: with 0.02 s, 10 Hz or 25 Hz; hence snapshots are keyed by `Clock.Step`, never wall time). Source's default is 20 snapshots/s with a 100 ms interpolation period, equal to two update intervals so one lost snapshot still leaves two to interpolate between ([Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)). NGO's default tick is 30 ([docs](https://mp-docs.dl.it.unity3d.com/netcode/1.8.1/components/networktransform/)).
- Buffer: render time = latest-received host time minus **3 snapshot intervals (150 ms)** as default (one more than Valve's 2, because heavy bodies have no gameplay need for low latency and the Steam relay adds jitter); allowed range 100-250 ms, tuned from M-056 results. Delay is one fixed number per session, not adaptive per frame.
- Snapshot content per body: `EntityId`, host step, position, velocity, yaw, yaw rate (velocity terms allow cubic Hermite interpolation and bounded extrapolation).
- Missing snapshot: Hermite-extrapolate from the last one for at most 250 ms (*Assumed*), then freeze and flag `net_log` "stale"; never teleport on a late arrival: blend toward truth over >= 250 ms with a critically damped correction.
- Clock: client render clock advances at constant rate locked to the Core step; a slewing correction of at most 1% toward the host clock (*Assumed*) avoids steps. Offsets measured by the handshake and by ping-pong in the snapshot stream.

**Pixel-grid stability.** Interpolate in world space in full precision, apply the camera, and only then snap to the output pixel grid in screen space (round the projected position of the body anchor to the nearest output pixel, with +-0.25 px hysteresis to stop a body toggling between two pixels). Never snap the network state itself, never apply interpolation to already snapped positions, and do not let the correction blend or clock slew change direction inside one pixel. Result: a remote body moves in clean 1-px steps at constant cadence, with no network-driven shimmer. The pixel size and output resolution come from the rendering contract (not read here); M-056 measures in output px so the metric does not depend on them.

## 4. Intent path and tick rate

1. Client samples its input on the Core step and builds `IntentPacket@v1`: (`PlayerSlot`, client step `n`, sequence `s`, last host step seen `h`, intent payload as defined by the T-005 `Control` seat contract).
2. Sent unreliable at the step rate (60 Hz) with the previous 2 intents repeated (loss cover, *Assumed*); 3 intents x ~16 B is small. Reliable channel only for handshake, join/leave and rare discrete commands.
3. Host drops stale packets (`s` <= last accepted for that slot), buffers by `s`, and at the start of each host step hands the newest valid intent per slot to the intent seat. If none arrived, the seat keeps the last intent for at most 100 ms (*Assumed*) then falls to neutral (stop command); `net_log` records both cases.
4. **Arbiter with two clients.** Net does not arbitrate; it delivers per-slot intents to the seat in ascending `PlayerSlot` index order (deterministic, independent of arrival order) in one step. The T-005 arbiter owns conflict policy (e.g. two slots commanding one body). Because arrival timing differs from step timing, resolution uses the host step at which each intent is applied, never client send order; this makes the outcome independent of RTT differences between clients. The latency-fairness question (does a lower-RTT client win ties?) is Q-NEW-c.
5. Tick: the host steps the sim on the Core clock (`Clock.Step`, one `FixedUpdate`); `h` and `n` are Core steps, so all net events are expressed in steps, matching `net_log` and replays. `fixedStepSeconds` must be identical on peers (checked in the handshake).

## 5. Join handshake (refuse on mismatch)

`SessionHandshake@v1`, over the reliable channel, before any gameplay data:
- Client -> host `Hello`: `protocol` (Net version), `contracts` (a name->version map taken from `CoreContractVersions` plus the Net contracts: IntentPacket, StateSnapshot, handshake), `flagsCanonical` = `FeatureFlagSnapshot.ToCanonicalString()`, `flagsHash` (SHA-256 of the canonical bytes), `fixedStepSeconds`, `buildVersion`.
- Host compares: (1) `protocol`; (2) every contract version, equal (not "compatible": contracts are `@v1` now, a bump means refuse); (3) `flagsCanonical` string equality (ordinal; it is already ordinal-ordered and fixed per session); (4) `fixedStepSeconds` bitwise equal; (5) `net.coop` is on in both. A mismatch yields `Refuse{code, details}` where `details` lists the differing contract names and flag names (host diffs the two canonical strings; clients never self-diff). Then the host closes the connection.
- The hash is sent so a mismatch is cheap to detect and the full string only travels on mismatch or in `net_log`. Build version differing alone is a warning, not a refusal, unless contracts differ (*Assumed* policy; Q-NEW-d).
- Accept returns the slot assignment, host `Clock.Step`, step length, and the first full snapshot. Slots: dynamic `PlayerSlot.Range(n)`, no maximum in Core, so the host's own cap (default 4, config) is the only limit.
- A client with the same flags but a loaded-from-save different world must also compare a world/scene id; deferred to the Track 3 task (Q-NEW-e).

## 6. Draft metrics

### M-055 intent-to-host latency at simulated RTT
- **Definition:** time from the client sampling an intent (client step `n` wall clock) to the host applying it in the seat; per intent, in ms; report p50, p95, max; also in host steps.
- **Procedure:** two peers over the loopback `ITransport` with a deterministic delay/jitter/loss wrapper (config: RTT 50, 100, 150 ms; jitter +-10 ms; loss 0% and 2%); client emits a scripted intent stream at 60 Hz for 60 s per cell (3 RTTs x 2 loss). Timestamps from the Core step clock and a simulated wall clock; no real sleep. Also run a short real-socket check on one machine for sanity (loopback only; delay injection is not claimed to match Steam).
- **Threshold (*Assumed*):** p95 <= RTT/2 + 34 ms (one-way delay + 2 steps of 16.7 ms); i.e. 59 / 84 / 109 ms at RTT 50 / 100 / 150; no intent applied twice or out of order; at 2% loss p95 may exceed this by at most one resend (<= +17 ms).
- **Source:** the structure follows Valve's description that latency = network + interpolation + processing ([Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)); the numbers are ours.

### M-056 remote-body error in output pixels
- **Definition:** on a client, for each rendered frame, the distance between the pixel position of a remote body as rendered and the pixel position of the host's true state **at the same simulated instant** (host state at render time minus the buffer, looked up from a host-side history), measured after the pixel-snap in section 3, in output pixels at the gameplay camera distance and output resolution. Report p95 and max over the run.
- **Procedure:** host moves two bodies on scripted paths (straight, slow turn, stop/start at peak acceleration); client runs at RTT 100 ms +-10 ms jitter and 2% loss; 120 s; measure at the project's gameplay camera distance and output resolution (read from the rendering contract by the task). Add a stress cell: RTT 150, 5% loss, with a forced 400 ms outage.
- **Threshold (*Assumed*):** steady cell p95 <= 1 px, max <= 2 px; stress cell max <= 4 px and recovery to <= 1 px within 1 s of the outage ending; no jump larger than 1 px between consecutive frames except at the outage.
- **Source:** none; px conversion is projected size = world error x focal px / distance (pinhole), the camera numbers come from the render config.

### M-057 bandwidth per client at N = 2 and 4
- **Definition:** bytes/s per connected client on the wire for downstream (host -> client) and upstream, **including** protocol headers added by us; Steam's own per-packet overhead is added as an *Assumed* 60 B/packet (IP+UDP+SNS headers) rather than measured, until a real Steam run replaces it.
- **Procedure:** host with N slots, N bodies + 1 kaiju + 8 further slow bodies, 20 Hz snapshots, 60 Hz intents; 120 s steady state and one 10 s join burst; count payload bytes at the `ITransport` boundary, per client and per direction; report mean and p99 per second.
- **Estimate (*Assumed*):** body record 32 B (id 4, pos 12, vel 12, yaw+rate 4) x (N + 9 bodies) = 416 B at N=4 (352 B at N=2), plus 12 B header + 60 B overhead = ~490 B/packet x 20 = ~9.8 kB/s down at N=4 (~8.5 at N=2); upstream 3 x 16 B + 60 B = ~108 B x 60 = 6.5 kB/s. Delta/quantisation would cut it; not planned for M1.
- **Threshold (*Assumed*):** down <= 64 kB/s and up <= 16 kB/s per client at N=4 (about 6x margin over the estimate); N=2 <= 80% of N=4. Host upstream = N x down.
- **Source:** none; ~20 snapshots/s is Valve's default rate ([Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)).

## 7. Testing two peers in one Unity batch process

Constraint: the machine allows at most two Unity batch processes, so the default is **one process, two peers**.
1. **Engine-free first (T-029, dotnet).** Two `NetSession` instances (host, client) in one test, joined by a loopback `ITransport` pair with the delay/jitter/loss wrapper; the sim is stepped manually with Core's `SimulationClock`. This covers handshake refusal, intent ordering, snapshots, M-055/M-057 and most of M-056 without Unity. Core's tests already run under dotnet.
2. **In-Unity (T-031, one process).** Our `Net` has no singleton, so two sessions and two `CoreServices` roots can live in one process only if the adapter avoids `CoreRuntime.Root` (the single static root) for the second peer: build the client peer from `CoreServices` (the engine-free root) without the static adapter, or give the client a separate registry. Run with a coroutine-free stepping loop in `[UnityTest]` EditMode or a PlayMode test. *Assumed* feasible; confirm in T-031 (Q-NEW-f).
3. **Two processes (optional).** Only when the machine has two free slots: host and client as two `-batchmode` players/Editor runs over local UDP (or Steam with two accounts, which needs the Steam client and is excluded from batch).
4. If NGO were chosen: its own test helpers create several `NetworkManager`s in one process ([docs](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/api/Unity.Netcode.TestHelpers.Runtime.NetcodeIntegrationTestHelpers.html)); that supports one-process testing there too, but the Steam transport stays untestable in batch.
