## 1. Question
How do we capture and encode footage and stills so store media keep the painted-pixel look (no resampling, dither intact, steady 60 fps), what shots show each pillar, and how do we gate fidelity (M-123, M-124)?

## 2. Headline
1. Capture **lossless, deterministic, frame by frame** (fixed timestep dump), never screen-record real time. Encode last, once, from the master.
2. **Integer scale only**, nearest neighbour, performed in one place (the present stage the project already has; `PixelCaptureRig` writes `color_internal` and `color_output`). The video encoder never scales.
3. Choose an **even integer scale so that every source pixel covers whole 2x2 chroma blocks** in 4:2:0; then H.264 yuv420p can keep one-pixel dither (to measure). Steam accepts H.264 up to 1920x1080 and transcodes it anyway [R-120 §5].
4. Store capsules: compose oversize integer-scaled, then crop.
5. Gates: M-123 = every capture frame passes M-003@v1 gated groups (and M-004 on clips); M-124 = decoded vs source ΔE00 ≤ 2.0 on ≥99 % of pixels. The 2.0 figure is **confirmed** (§7) as the project's existing M-003@v1 tolerance, not newly invented.

## 3. What the repo already provides (contract read)
- `StyleCapture` is an editor/batch tool: `unity run . -- -executeMethod Game.Tools.StyleCapture.StyleCaptureCli.Run -captureOut <dir> [-captureJobs] [-captureProfiles] [-captureCommit]`; output per frame `<stem>_color_internal.png`, `_color_output.png` (present stage), `_index.png` (palette index), `_depth.png`, `_mask_animated.png`, per-frame JSON sidecar, `sequence.json` manifest; the run throws if the log has any error; sets are deterministic and bit-identical across runs after a warm-up (HANDOFF session 3).

- Plan for T-147: a new file next to it (not an edit of its files) adds `capture_path@v1` (waypoints + times) and a driver that reuses `PixelCaptureRig` and the same sidecar schema, so M-003/M-004 tools read it unchanged. T-148 reads `*_color_output.png` for style checks and for encoding.
- The index image gives an exact palette-based check (M-003 index adherence) with no tolerance, stronger than ΔE.

## 4. Capture practice
### 4.1 Resolution and scale (Q-234)
- Let the internal frame be W x H (pixel pipeline guard band cropped). Output size 1920x1080 and 3840x2160 must be integer multiples of W x H, else crop (not stretch). If W,H do not divide 1920x1080, **render extra internal columns/rows and crop at the output** (an off-by-N crop is lossless; a fractional scale is not). Choose internal sizes with the factor lists: 1080 = 2^3 x 3^3 x 5, 1920 = 2^7 x 3 x 5; common pairs 480x270 (x4, x8), 640x360 (x3, x6), 960x540 (x2, x4). A pure 16:9 internal frame of 480x270 satisfies all store sizes, including 3840x2160 (x8). Record the actual choice in the capture plan (T-146); it is a look decision of the style track, not R-121's.
- Never bilinear, bicubic or Lanczos anywhere (M-003 controls: bilinear upscale measured 87.1 % vs ≥95 % required [R-002]).
- In ffmpeg, if a separate scale is ever unavoidable use `-vf scale=W:H:flags=neighbor` (the manual lists `neighbor` for `sws_flags`; `-scaler` is the newer option and `sws_flags` default is bicubic [ffmpeg-scaler]). Prefer scaling in the engine or with a Python/NumPy `np.repeat` pass so no filter default can creep in. Note ffmpeg's neighbour handling of the chroma planes differs slightly [tasvideos thread]; so scale in RGB before conversion to YUV.
### 4.2 Lossless masters
- Master = numbered PNG sequence (8-bit sRGB, no alpha, colour-profile-free, gAMA not written) of `color_output` at the target resolution, plus the internal-resolution PNGs; or FFV1/ProRes 4444 if the disc budget requires (PNG preferred: it is what the style tools already read and compare bit-exactly).
- Storage: 1080p PNG ≈ 1-3 MB flat-colour; 60 s at 60 fps = 3,600 frames ≈ 4-10 GB. Keep masters outside git (evidence folder git-ignored like `captures_local`), record hash lists (sha256 per frame) in the manifest.
- Determinism: run the same job twice and compare hashes (existing practice).
### 4.3 Frame pacing for 60 fps
- Do not screen-capture in real time. Drive the game with a fixed step: Unity `Time.captureFramerate = 60` (it forces `Time.deltaTime` = 1/60 and decouples game time from wall clock) or the project's own fixed-step driver, and write one frame per step. Physics (fixed step) and camera path sampling advance on the same clock.
- Camera path times are in seconds; sample at exactly n/60; no frame blending or motion blur (blur is a resample and breaks dither and M-004).
- Encode as constant frame rate 60 (store accepts 60/59.94). Use 30 fps only if the content fails M-004 at 60 (not expected). Avoid interpolating 30→60.
- Pixel stability: M-004 pixel shimmer/crawl metrics apply to clips; the Pixel pipeline's snap and direction anchoring (cycle-2 finding: `direction` mode is the shipping mode) must be on in capture.
- Steam's own player re-encodes; players may see 30 fps if bandwidth is poor; shot design must read at 30.
### 4.4 Stills (screenshots)
- Direct from the same driver at a fixed frame index, lossless PNG at 1920x1080 (min) or 3840x2160 (downscale-free: it is just a higher integer factor; Steam says ≥1920x1080 [R-120 §5]). Mind file size on upload (unknown limit; verify).
- Real gameplay only: HUD visible (rules: no concept art or pre-rendered stills). Frames must be actually produced by the game build; the camera path is a scripted player/camera, not a different renderer.
- Capsule art: oversize integer-scaled render + title logotype added in a hand-pixelled/vector layer, then crop to 920x430, 462x174, 1232x706, 748x896, library 600x900, hero 3840x1240. Library hero has no text.

## 5. Encode practice (Steam trailer)
- Target [R-120 §5]: mp4, H.264, 1920x1080, 60 fps, ≥5 Mbps (Valve's example 20 Mbps), AAC 48 kHz stereo, 16:9.
- Proposed command (to measure; scale is **already done** in the master):
```
ffmpeg -framerate 60 -i frames/%05d.png -i audio.wav -c:v libx264 -preset slow -crf 14 -tune animation \
  -pix_fmt yuv420p -colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv \
  -vf "scale=in_range=full:out_range=tv:in_color_matrix=bt709:out_color_matrix=bt709:flags=neighbor+accurate_rnd+full_chroma_int" \
  -c:a aac -b:a 192k -ar 48000 -movflags +faststart out.mp4
```
- Why these: `-tune animation` favours flat areas and longer references (suits flat palette art); low CRF keeps dither; BT.709 tags avoid a colour shift between viewers (a shift is a global ΔE error that M-124 would catch); `yuv420p` is the compatible format (Steam transcodes uploads regardless; keep the upload in the format that transcodes best). `yuv444p` is better in theory but H.264 High 4:4:4 Predictive is poorly supported by decoders and the Steam transcoder (unverified): test, do not assume.
- Chroma: 4:2:0 stores one chroma sample per 2x2 luma; at a scale of 1 a one-pixel dither of saturated colours is destroyed, at an even integer scale each 2x2 chroma block sits inside one source pixel, so the loss is limited to block edges and quantisation (the TASVideos advice to resize ≥2x before encoding is the same idea [forum]). Odd scales (3x) do not align blocks: prefer 2x/4x/6x/8x of the internal size where possible.
- Bitrate vs CRF: for one-off trailers use CRF with `-maxrate`/`-bufsize` only if the upload must stay below a size; otherwise ignore bitrate and verify ≥5,000 kbps for M-122. Flat pixel art at CRF 14 may land well under 20 Mbps; this is fine as long as ≥5,000 kbps (if lower, lower the CRF).
- Upscaling trick for 4K YouTube (ladder gives higher bitrate to 2160p) [ffmpeg YouTube wiki, via search summary]: separate asset for the founders' own YouTube channel; Steam path stays 1080p. Out of scope for M3 gating; mention in the capture plan.
- Audio: music/SFX come from the Audio module; trailer audio is mixed offline; no AI-generated audio unless provenance recorded (M-120).

| Variable | Values |
|---|---|
| Scale of master relative to internal | 1x, 2x, 3x, 4x |
| pix_fmt | yuv420p, yuv444p |

| Tune | none, animation |
Expectation (to measure): yuv420p at 1x fails dithered regions; yuv420p at ≥2x with CRF ≤ 18 passes ≥99 %; the chosen release setting is the cheapest cell with ≥99.5 % (0.5 % margin).

## 7. Metric drafts
### M-123@v1 · Every capture frame passes the style metrics
- Definition: for a capture set, share of frames (and of clips) that pass M-003@v1 gated groups (palette adherence ΔE00 ≤ 2.0 on ≥95 % of `color_output` pixels, ≥99.5 % of `color_internal`, dither present, depth-banding monotonic) and, for each clip, M-004@v1 (shimmer/crawl) in the shipping `direction` mode.
- Procedure: `Pipelines/capture` runs the existing `Tools/Metrics` M-003/M-004 functions over each frame/clip with the profile of the shot's district; a frame with no profile (e.g. menu, logo) is exempt only if listed in the plan as non-world (UI-only frames must pass index adherence for the UI palette).
- Threshold: **100 % of store frames pass** (a failing frame is replaced, not excused); evaluator panel of R-002's "blind panel ≥ 8/10" runs on the final screenshot set once, by the evaluators, not by script.
- Source: M3 plan; R-002 F1.
### M-124@v1 · Encode fidelity
- Definition: for each decoded trailer frame (ffmpeg decode to RGB, same colour tags) vs the corresponding master frame: share of pixels with CIEDE2000 ΔE ≤ 2.0; metric = minimum over sampled frames and mean.
- Procedure: decode every 10th frame plus all scene-cut frames (100 % on ≥60 frames), convert to CIELAB (D65, 2°, same as R-002), CIEDE2000 (Sharma et al. 2005 implementation, already in `Tools/Metrics`), ignore nothing. Also report the 99.9th percentile ΔE and global mean shift (detects a colour-matrix error). Compare against the master at the encoded resolution.
- Threshold: **≥99 % of pixels ≤ 2.0 for every sampled frame** (task proposes 99 %); and report, do not gate, the 99.9 % number.
- Confirmation of 2.0: CIEDE2000 is designed so 1.0 ≈ one JND by convention; CIE76's JND was later revised to ~2.3; the project already derived ΔE00 2.0 as 2x the design JND and above 8-bit rounding noise (max 0.88 measured) in `research/R-002.md` F1 [wiki ΔE; Sharma 2005; R-002]. So 2.0 is imperceptible-to-barely-visible and consistent across M-003 and M-124. The 99 % share is a **pragmatic** figure (cuts frame edges and fade pixels); no external source fixes it. Derive/validate empirically from §6: if the cheapest acceptable cell shows ≥99.5 %, keep 99 %; never lower it to pass.
- Limit: Steam transcodes our file again; M-124 certifies **our** upload, not what Steam serves (not controllable).
