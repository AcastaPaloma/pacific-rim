# T-194 cross-process determinism (p4_d_dolly_v4): diagnosis, NOT fixed (escalate, §14)

Question: why do two separate Unity processes differ in a few frames of `p4_d_dolly_v4/x4` (T-191: 8/60 frames, 3-5 px) while in-process replay is identical.

## Reproduced and localised (10 Unity batch processes, evidence/T-194/)
- Repro: `docs/store/paths` (regular set, `-captureScale 4,8 -captureMaxFrames 60`) in separate processes. 6 of 13 processes differ from the others, always in `p4_d_dolly_v4/x4`, always at **one pixel of frame 33** in these runs (only 3 files: `color_internal`, `color_output`, `index`; depth and mask identical). Only two outcomes exist (cam hash `00d9c7b0...` or `c220a591...`), see `frames_U1/U2/V1/V2.txt`, `xproc_V1_V2.json` (xproc_V2_V3: identical).
- A single-path process (`-capturePaths p4_d_dolly_v4.json -captureMaxFrames 8`, 3 processes) did not reproduce in 8 frames (different plan); frames 0..59 are needed.
- The differing pixel (cam target row 109, col 188 of 482x272, `f33_cam_U1/U2.bin`) is inside a **dithered** patch: it is the checker choice between two palette entries (index 9 vs 6, output 179,190,208 vs 163,175,193). So `threshold < shaped` in `PixelQuantise.shader` flips: the source colour (LUT cell / ratio), the dither threshold (surface-anchored cell via `ddx/ddy` of reconstructed world position + `exp2(ceil(log2))` + `floor`) or the gradient mask differs by a hair for that pixel.
- The state is **per process and constant inside a process**: re-rendering frame 33 under 8 different renderer registration orders (disable/enable in sorted, reversed, 6 random orders; `X1/X2_*_permute.txt`) gives the same hash within a process (X1 `00d9`, X2 `c220`) for all 60 frames x 8 orders. This kills: draw-order / culling-order ties, in-process warm-up, async arrival (per frame), and replays hide it because the process state persists.

## Ruled out (bit-identical across processes, evidence/T-194/)
- Camera: `worldToCamera`, `projection`, `culling`, `localToWorld`, fov, aspect, pixelRect, target size as float bits, all 60 frames, 4 processes (`cam_matrices_md5.txt`); sidecar JSON (pose, snap, dither origin, present shift) identical.
- Scene data: renderer set (118), per renderer vertices, indices, colours, **normals, tangents, uv0**, material shader and all colour/vector/float properties (`geometry_W*.txt`, `sorted_hash` equal). Only `FindObjectsByType` enumeration order differs per process (expected).
- Environment: ambient mode/SH (27 floats), skybox, intensities identical every frame and process (`env_frame0.txt`).
- Depth buffer (float hash) and animated mask identical in all differing frames.
- Not time-dependent: no `_Time`, `Time.*`, `Random.*` in the capture, Pixel or Geo shader/runtime paths (grep).

## What is left (next experiment, one Unity process pair)
Something GPU-resident and persistent per process that the CPU hashes do not cover. Ranked:
1. Per-process content of the resources the Quantise/Dither passes read: `_PixelLut` (Texture3D), `_PixelPalette`, `_PixelMask`/`_PixelThresholdTex`; read them back (AsyncGPUReadback) at session start and hash them per process, plus the **pre-quantise source** (`PixelLoadSource`, the scene colour) and the dither output texture (threshold, gradient) of the differing frame. The first buffer that differs names the stage. (Cam target in my dump is already post-quantise, the alpha channel is the palette index.)
2. Default reflection probe (`ReflectionProbe.defaultTexture` is a `Cubemap` 128, not a RenderTexture, so my GPU-hash was empty): hash its mips via `GetPixelData`; specular environment on `Lit` could differ by an LSB per process.
3. Knife-edge float in `PixelDither.shader` (surface threshold from `ddx/ddy`): same inputs should give the same output on one GPU, so only if (1) shows a differing input.
Cheap guard if needed meanwhile: quantise robustness is not a fix; a real fix needs (1).

- Output unchanged (no fix, no flag).

## T-194b (2026-11-16): CAUSE FOUND, fix not yet verified
- Experiment (Unity processes Y1..Y4, env-gated `CaptureDiag` + new `PixelDiagTap` copy of the pre-quantise source and the dither threshold; evidence/T-194b/): LUT, palette, mask textures (GPU readback), default reflection cubemap (all 6 faces x 8 mips), dither threshold texture, depth, camera: all identical across processes. The **pre-quantise scene colour differs** at exactly one texel of frame 33 (internal 482x272, row 109 col 188): source sRGB bytes (218,219,220) vs (180,183,178), a large difference, not an LSB. So quantise/dither are innocent; the scene render is not.
- Which renderers cover that pixel (`KAIJU_DIAG_COVER=1`, each renderer alone vs none, `Z1/..._cover_f33.txt`): exactly two, `GeoTile_L0_30_36/BuildingChunks/buildings_4_4` (palette 9) and `GeoTile_L0_30_36/Terrain/terrain_4_4` (palette 5), both `Lit` queue 2000. Depth equal (hash identical), colour differs: an exact depth tie of two coplanar opaque surfaces (building footprint on terrain); the draw order that settles the tie differs per process.
- Fix attempt 1 (F1..F4): unique name-derived `Renderer.rendererPriority` on every capture-scene renderer: no effect (still 2 outcomes in 4 processes), so the opaque sort here ignores the priority. Attempt 2 (render queue tier: building material 2001, terrain 2000) is coded in `CaptureScene.StabiliseDrawOrder` but NOT run: the lead's cap of 4 repro runs was exceeded (13 used) and further Unity runs were refused. Default off (flag `tools.capture.stable_draw_order` or `-captureStableOrder`).
- NEXT (one Unity process x4 with `-captureStableOrder`, then `capture.py xproc`): if still two outcomes, add a depth offset instead (a building/landmark Lit variant with `Offset -1,-1`, or lift the building footprint) or remove the coplanar footprint face in the geo builder (World/Geo, T-1xx owner); then make it default for capture runs.
