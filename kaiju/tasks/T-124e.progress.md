# T-124e notes (stage-0 hitch attribution), branch task/T-124e
## Result: the stage-0 hitches are external stalls, not the scheduler and not JIT
- Run 1 (seed5_phases, load 8 -> 34): of 40 logged hitches >12 ms, the stage-0 ones are two events: 61.1 s stage 0 = 21.4 ms with ONLY scheduler phase 0 (clusters) = 21.39 ms and the other phases 0.00-0.04 ms, and 506.0 s stage 0 = 32.1 ms with ONLY phase 1 (wanted set) = 32.07 ms (steady 0.06 ms). A single phase spiking 300-500x while its neighbours stay at steady state is not an algorithm cost. Other strm hitches are stage 5 (Pump tile build 10-38 ms, real work) and stage 1 (Release/evict 92.9 ms once). Physics (phys 12-85 ms) and destruction (36-110 ms) show the same isolated stalls in unchanged code; they cluster at 506-620 s, when another worker's 12-process Python job arrived (load 34).
- Run 2 (seed5_cpu, load 25-39, thread CPU time added): all 40 logged hitches (62-86 s) have wall 12-295 ms while the main thread used 0.4-1.6 ms CPU. So the thread was off-CPU (descheduled by machine load, or suspended/blocked) for the whole excess; compute, JIT and algorithm cost would burn CPU. gcd (gen0 collections during the frame) is 1 in about half and 0 in the rest, so a stop-the-world GC triggered by a background thread explains part, preemption the rest; not separable at this load. Scheduler phases: one phase carries the whole stall wherever the frame happened to be (phase 0 is the first timed section of Tick, hence most often).
- Verdict for M-008.c: the stage-0 hitches are machine load and GC suspension, not code to optimise. A quiet-machine run (load < ~4) is still needed to bound the remainder; with load 8-39 here p99 is 4.3 ms (run 1) and 9.95 ms (run 2), frames > 33.3 ms 16 and 72 (T-124c baseline 3 on this seed at load 5), i.e. the advisory c clause scales with machine load. No threshold touched, no default flipped.
- Observation: in three runs now (T-124c opt_v2 seed 5, T-124d, run 2) a hitch cluster sits in 61-92 s, right after the warm-up. Not proven to be load (run 1 had none there). Candidate: the first minutes after warm-up are when the foci start moving and the tile builder threads allocate (GC from another thread). A per-frame `gcd` with a quiet machine would settle it.
