# T-160 · full-physics kaiju locomotion: staged plan (T-160 to T-175)

Source research: `research/R-130.md` (targets, three body plans Q / B / T, the lessons from T-005, Q-250 to Q-259, M-130 to M-132). Breakdown: F-023, F-024, F-009 (kaiju part), F-021 (motor layer), M-001 / M-002 (extended by M-130), M-006, M-007 / T-041 (the RL interface only).

Ambition: every body plan (quadruped Q, upright tailed biped B, horizontal tail-balanced biped T, plus tripod and limb-loss modes) walks under pure physics at 80 m / 10,000 t and scales to the D-026 species. Order: Q → T → B (Q-254). Nothing is cut; later items are staged behind gates.

## Rules (the T-005 rules, applied to kaiju)
- **No assist.** No external stabilising force, no kinematic root. Bodies move only by drives, torques, contacts, gravity and logged external forces (`IArticulatedBody` contract).
- No threshold edits and no lower bands to make a gate pass; a failing gate is reported, not relaxed.
- **No edits to T-005 files.** That covers `tasks/T-005*`, `Config/Mech/*`, `Tools/GaitOpt/*` (read or import only) and every file `task/T-005` touches under `Assets/Game/Physics/Body/` (`MODULE.md` gets a kaiju row only at merge time, after T-005).
- Kaiju code is behind feature flags (`Config/FeatureFlags/KaijuLocomotion.json`: `kaiju.locomotion.enabled`, `kaiju.locomotion.qp`), default off.
- Workers are Sonnet at medium effort (Haiku for pure data plumbing), one task each, from the QUEUE brief template. Opus is used only at the escalation points below.
- Python only through `/opt/miniconda3/envs/kaiju/bin/python`; Unity runs in the background through ScenarioCli; commits only through `Tools/agent/commit.sh` under the shared merge lock.
- Every run writes `gait_log@v1` + `physics_log@v1` (Python and Unity alike) so one metric toolchain scores both.

## What is gated behind T-005
- **Hard gate (Unity, T-172 to T-175):** T-005 merged to main. T-005 owns `ArticulatedBody`, `BodyWorld`, the mass-unit plumbing, `physics_log@v1` and the PhysX project settings; the kaiju body extends them.
  - Equivalent founder ruling: T-005 reaches 9.5 (one stable QP walk at Fr 0.10 in Unity) and the founders allow kaiju Unity work on a branch from `task/T-005` before the merge.
- **Soft gate (T-171 merge):** `GoldfarbIdnaniQp` on main (Q-258).
- **Information gate:** if T-005 round 4 ends with the QP not walking in Unity, T-173's risk rises. The kaiju still proceeds offline, because Q's smooth, statically stable creep is a different problem from the mech's impulsive toe-off (R-130 §6.3). The T-005 final report must be read before T-172 starts, and its PhysX findings folded into T-172's brief.

## Go / no-go stop rules
1. **T-165 feasibility.** If Q is infeasible at Fr 0.08 under the frame's limits, stop. Report the binding constraints (body data, for the founders: pad size, leg torque, ROM). No tuning loop.
2. **T-166 offline go/no-go (Q).** At most **3 diagnose → fix → run cycles** to pass A, B and C on both contact variants.
   - No pass → stop; no T-167, T-168 or T-171 work. Escalate (point 2).
   - After the escalated cycle, still no pass → `evidence/T-166/REPORT.md` with a founder question. Options: body data (β, pad, limb), a different formulation (full-ID for Q), or an interim creep-only Q (Fr ≤ 0.05). Never an assist.
3. **T-167 per plan.** Same 3-cycle bound per plan. A failing B does not block T. A failing T and B does not block the Q-only Unity path (T-172 / T-173).
4. **T-173 Unity go/no-go.** At most 3 cycles to one stable cruise at Fr 0.08. If none is stable, stop and report (escalation point 3). T-174 and T-175 do not start.
5. **Continuation rule** (T-166 C, T-173, T-174): stop after three consecutive failed Froude increments, as T-005.
