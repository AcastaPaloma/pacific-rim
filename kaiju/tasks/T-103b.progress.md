# T-103b progress (M2 Track 1; branch task/T-103b): Bay-wide building-height fill (lidar DSM)

## Goal
M-005@v2 default-height share <= 2 % Bay-wide and per county (was 74.0 %, T-106). Thresholds are not lowered.

## Tools (new, Pipelines/geo)
- `fetch_lidar_bay.py` plan | run | report: reads 3DEP EPT first returns only in the 128 m cells that hold a still-`default` building (runs of up to 4 adjacent cells = one PDAL read, bounds in BayTM masked exactly), newest project first, the next project only for buildings below `lidar_fill.min_coverage` (0.70) coverage; keeps ONLY the reduced 1 m grid (p95, max, multi, count) as `cache/lidar/rind_v11__<tile>.npz` (the file `bake.bake` already reads, same keys; 1 m only). No point cloud is stored. Tiles that already have a rind_v11 file are never touched. Retries transient S3/ept.json failures (5x back-off).
- `fetch_lidar_lpc.py run`: for the tiles outside every EPT project: TNM `Lidar Point Cloud (LPC)` index per tile, LAZ downloaded to `cache/lidar_bay/lpc_tmp/`, reduced, deleted at once.
- `run_lidar_bay.sh`: chain, per county: fetch (disk guard 25 GB) -> `bake_bay.py --stage l0 --force --tile ...` for the tiles it filled (list in `cache/lidar_bay/baked.txt`). LOD is NOT run.
- State: `cache/lidar_bay/{plan.json,status.jsonl,status_lpc.jsonl,summary.json,chain.log,baked.txt}`; env `KAIJU_GEO_CACHE` = integration cache (`.../fable-orchestrator-prompt-83a0a8/kaiju/Pipelines/geo/cache`).

## Findings while running (2026-11-15 evening)
- PDAL's EPT reader aborts the whole process (uncatchable C++ `pdal_error`) on a transient S3 read of an `ept-hierarchy` json. Fix: every EPT read runs in a child process (`fetch_lidar_bay.py readrun ...`), retried 5x with back-off; a tile is never lost to one S3 blip. Orphan pool workers from killed runs finish their tile and write a valid rind file but no status line: harmless, the next run skips a tile that already has a rind file.
- Rate (first 7 big Alameda tiles, 5 workers, machine load 20-40 from other sessions): about 520 s per tile, 5-7 default buildings/s per worker; full Bay (1.38 M default buildings) estimated 12-18 h. Output so far 12 MB per tile on average, so the grids total about 10-30 GB at most; the 25 GB guard stops the batch cleanly (chain exit 3).
- Satisfied by lidar: 11,916 of 11,978 targets in the first 7 tiles (99.5 %). Buildings the lidar cannot cover (< 70 % of the eroded footprint with first returns, or vegetation test) fall to the next project, then stay `default` (flagged, never invented).
- Contra Costa fringe (48 tiles; plus Sacramento 23, Yolo 5, San Joaquin 3, San Mateo 2, SF 1 = 82 tiles, 12,460 default buildings, 3.56 km2 of footprint): no EPT project at all (CA_ContraCosta_1_2022, CA_ContraCostaCo_2007, Solano, San Joaquin all return no points there, checked on L0_60_44). TNM LPC has CA_Central_Valley_LiDAR_2016_D16 (LAZ 1.7 km files of 100-150 MB, newest, QL2) plus the 2007 Contra Costa legacy set. `fetch_lidar_lpc.py` downloads the needed files one at a time, reduces and deletes them. rockyweb.usgs.gov answers HTTP 429 when hit fast and then serves only about 100 KB/s, so the 82 tiles (about 130 files, about 15 GB) take 1-2 days of one stream. It is running in the background (`status_lpc.jsonl`, `lpc_run.log`, biggest default area first: L0_60_44 1806 buildings, L0_64_42 1802, ...). If it is too slow, what remains stays `default`; the per-county Contra Costa clause then depends on its share of the fringe (finding for the owner: a faster mirror, e.g. a different TNM host or OpenTopography, would fix it; nothing licence-related blocks it, USGS public domain).
